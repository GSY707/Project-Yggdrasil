# UX 设计团队交接准备文档

日期：2026-06-04

## 1. 当前判断

当前 Web 工作台已经不再只是空壳：任务创建、应用模板、素材导入、首次启动检查、本地发布边界和数据位置说明都已经进入界面。问题不再是“没有 UI”，而是 UI 仍然像一个把能力全部摊开的操作台。

如果找专业团队，不能只让他们做视觉美化。更应该让他们做产品入口重构、信息架构、关键任务旅程、术语体系、设计系统和未来发行形态规划。

当前应坚持的产品方向：

- 普通用户默认走 GUI-first。
- CLI 保留为高级、调试、自动化和内部运维路径。
- 不为了兼容旧控制台继续叠补丁；新用户路径应直接切到产品化入口。
- 未上线能力必须标为计划中，不能在设计或文案里伪装成已支持。

## 2. 为什么现在像功能堆积

### 2.1 导航把不同用户混在一起

当前侧边栏同时暴露总览、任务、节点、协作、资产、训练、应用、MCP、Prompt、评测、观测、发布与安全等入口。这些入口覆盖普通用户、开发者、运维、评测人员和系统维护者，但视觉权重接近。

结果是用户看到的是“系统有哪些模块”，不是“我现在要完成什么事”。

应重构为：

- 普通用户主线：开始、任务、素材、应用、结果、数据。
- 高级模式：Prompt、MCP、评测、观测、协作、训练。
- 开发者 / 运维模式：健康、日志、迁移、备份恢复、调试。

### 2.2 主流程已经存在，但被控制台语境包住

已有入口：

- `apps/web/app/components/task-launch-panel.tsx`：应用模板创建并启动任务。
- `apps/web/app/components/tasks-page.tsx`：任务创建、启动和任务列表。
- `apps/web/app/components/assets-page.tsx`：文本素材导入、切段预览、附加到任务。
- `apps/web/app/components/applications-page.tsx`：应用清单、激活和新建任务入口。
- `apps/web/app/components/application-detail-page.tsx`：应用详情、用户级重要设置和应用任务启动。
- `apps/web/app/components/release-page.tsx`：本地产品模式、数据位置、备份恢复和未来发布模式。

这些入口说明产品路径已经成形，但页面仍大量显示内部对象：appId、branchId、spaceId、module、Prompt profile、runtime、observability、provider key、queue 等。普通用户还需要理解系统结构，才能判断下一步。

### 2.3 页面视觉像 dashboard，不像任务产品

当前界面大量使用卡片、状态徽标、内部字段、统计卡和技术说明。它对开发者排查很有用，但对首次用户会造成认知负担。

典型表现：

- 页面标题很大，但页面内同级区块过多。
- 主要动作和次要动作常出现在同一层级。
- 同一页面同时承担 onboarding、创建、状态、调试和说明。
- 高级字段默认可见，普通用户难以区分哪些必须填写。

### 2.4 应用包还没有完全变成“产品场景”

应用包已经有模板、示例任务和预期产物，但用户仍会看到内部应用 ID、模块数量、场景数量和配置字段。设计团队需要把应用重新表达成“我想完成的工作”，例如：

- 做一次深度研究。
- 继承一个代码项目。
- 写一个长篇故事章节。
- 整理知识库。
- 训练或评估一个工作流。

### 2.5 未来形态还没有进入信息架构

项目已经把以下形态列入路线：

- 本地产品模式。
- 完整 Docker Compose 产品栈。
- 桌面封装。
- 删除 / 清理 / 数据治理。
- 托管 / SaaS。
- 官方远端数据托管、备份、恢复和删除。

这些不是单独的功能页问题，而是会影响整个产品设计：

- 用户在哪里登录或选择本地模式。
- 数据在哪里保存。
- 什么会离开本机。
- 如何备份、恢复、删除。
- 本地、桌面、自托管、SaaS 的入口是否一致。

## 3. 找设计团队前要准备的材料

### 3.1 一页产品定义

必须先写清楚：

- 产品一句话：这个系统帮谁完成什么高价值工作。
- 首批目标用户：外部普通用户、技术用户、内部维护者分别是谁。
- 第一个成功体验：用户第一次打开后，多少分钟内应该完成什么。
- 不做什么：哪些能力暂时只放高级模式或计划中。
- 产品形态判断：Web-first / local-first，CLI 是高级通道。

建议给设计团队的版本：

> 世界树计划是一个本地优先的 LLM 工作台，用户通过应用模板导入素材、创建任务、观察运行、获得可恢复的长期工作结果；开发者和高级用户可以进入 CLI、Prompt、MCP、评测和观测层做深度控制。

### 3.2 目标用户和场景

至少准备 3 类用户画像：

| 用户 | 主要目标 | 不想处理的东西 |
|------|----------|----------------|
| 普通试用者 | 快速完成一个研究、写作、代码或知识整理任务 | 多服务启动、环境变量、内部 ID、评测术语 |
| 高级用户 / power user | 调模型、改应用配置、复用任务、管理素材和记忆 | 无法解释的黑盒和不可恢复状态 |
| 开发者 / 维护者 | 调试服务、Prompt、MCP、评测、观测、备份恢复 | 被普通用户界面隐藏关键内部状态 |

每类用户准备 2-3 个真实任务例子，而不是抽象功能列表。

### 3.3 当前界面资料包

交付给设计团队：

- 当前 Web 路由列表。
- 关键页面截图或录屏。
- 当前 demo 截图：`apps/web/public/demo/yggdrasil-p2-tasks.png`、`apps/web/public/demo/yggdrasil-p2-assets.png`、`apps/web/public/demo/yggdrasil-p2-release.png`。
- 当前主组件位置：
  - `apps/web/app/components/sidebar-nav.tsx`
  - `apps/web/app/components/overview-page.tsx`
  - `apps/web/app/components/task-launch-panel.tsx`
  - `apps/web/app/components/tasks-page.tsx`
  - `apps/web/app/components/assets-page.tsx`
  - `apps/web/app/components/applications-page.tsx`
  - `apps/web/app/components/application-detail-page.tsx`
  - `apps/web/app/components/release-page.tsx`
  - `apps/web/app/globals.css`
- 当前用户采用度审计：`docs/development/USER_ADOPTION_SURFACE_AUDIT_2026_06_03.md`。
- 当前发布与远端数据规划：`docs/development/PRODUCT_PACKAGING_AND_REMOTE_DATA_REQUIREMENTS_GAP_2026_06_04.md`。

### 3.4 功能真相表

设计团队最怕按错误能力设计。需要准备一张功能真相表：

| 能力 | 当前可用 | 计划中 | 不应承诺 |
|------|----------|--------|----------|
| Web 创建并启动任务 | 是 | - | - |
| 应用模板 | 是 | 可继续产品化 | - |
| 文本素材导入 | 是 | 更多文件类型 | 当前不应宣称完整多媒体导入 |
| 本地产品一键启动 | 是 | 更稳定包装 | 不应宣称安装包 |
| 完整产品 Docker Compose | 否 | 是 | 当前 infra compose 不是产品发行物 |
| 桌面安装包 | 否 | 是 | 不能画成已支持 |
| Web 删除 / 清理 | 否 | 是 | 不能给危险删除按钮 |
| SaaS / 官方远端数据 | 否 | 是 | 不能承诺账号、同步、远端备份和 uptime |

### 3.5 关键用户旅程

要求设计团队先画流程，不要先画视觉稿。

必须覆盖：

1. 首次打开产品：检查环境、provider、数据位置，进入第一个任务。
2. 导入素材：选择文件或粘贴内容，预览切段，附加到任务。
3. 选择应用：从用户目标选择应用，而不是从 appId 选择模块。
4. 创建并启动任务：模板、目标、预算、模型、权限、启动状态。
5. 任务运行中：进度、当前焦点、可暂停 / 恢复 / 安全停止、错误修复。
6. 查看结果：产物、证据、后续动作、继续任务或导出。
7. 配置应用：普通设置与高级 JSON / Prompt 分离。
8. 数据管理：数据位置、备份、恢复、删除预览、远端边界。
9. 高级调试：Prompt、MCP、评测、观测、协作如何进入高级模式。

### 3.6 术语表和命名边界

准备两套词表：

- 用户词表：任务、素材、应用、结果、记忆、备份、恢复、数据位置、成本预算。
- 高级词表：appId、branchId、spaceId、Prompt、MCP、evaluation、observability、module、runtime、mailbox、side-channel。

设计要求：

- 用户首屏优先使用用户词表。
- 高级词表进入“高级模式 / 调试详情 / 开发者视图”。
- 不要把内部里程碑名、测试名、协议名当作用户导航。

### 3.7 数据与信任边界材料

未来发展会碰到本地、桌面、自托管、SaaS 和远端数据。设计前必须准备：

- 本地数据保存位置。
- 密钥保存位置。
- 什么内容会发送给 LLM provider。
- 什么 trace 或日志可能发送到 Langfuse / OTel。
- 当前备份和恢复方式。
- 当前没有 Web 删除和远端删除。
- 未来远端同步必须显式开启。
- 删除、备份、恢复、账号退出的长期目标。

这部分不能后补。它会影响 onboarding、设置页、发布页、数据管理页和 SaaS 账号体系。

### 3.8 技术与交付约束

给设计团队明确：

- 前端是 Next.js，主代码在 `apps/web`。
- 当前组件是自定义 CSS 和 React 组件，不是成熟设计系统。
- 需要交付设计 token、组件状态、响应式规则和实现优先级。
- 卡片、表单、状态徽标、导航、空状态、错误状态、加载状态都要规范化。
- 需要区分普通用户模式和高级模式。
- 不能要求通过兼容旧 UI 逐步套壳，应该允许重排页面结构。

### 3.9 成功指标

建议给设计团队以下验收指标：

- 新用户从打开 Web 到启动第一个任务的时间。
- 不看 README 能否完成首次任务。
- 用户能否说清楚数据在哪里、什么会出机。
- 用户能否区分“创建草稿”和“创建并启动”。
- 用户能否从应用模板判断哪个适合自己。
- 用户能否理解任务失败后下一步怎么修。
- 高级用户能否在不干扰普通入口的情况下找到 Prompt、MCP、评测和观测。

## 4. 应要求设计团队交付什么

建议把外包或专业团队交付物拆成 6 组。

### 4.1 产品信息架构

交付：

- 一级导航重构方案。
- 普通模式 / 高级模式 / 开发者模式分层。
- 页面地图。
- 每个入口的用户目的和权限边界。

验收：

- 普通用户打开后能直接知道下一步。
- 高级工具没有消失，但不会压住主流程。

### 4.2 关键流程原型

交付：

- 首次启动流程。
- 应用选择流程。
- 素材导入到任务流程。
- 任务创建、启动、运行、失败恢复和结果查看流程。
- 数据管理、备份、恢复、删除预览流程。

验收：

- 至少做可点击 Figma / prototype。
- 每个流程有空状态、错误状态、加载状态和成功状态。

### 4.3 视觉设计系统

交付：

- 色彩、字体、间距、圆角、阴影、密度。
- 导航、按钮、表单、卡片、列表、状态徽标、表格、代码块、通知。
- 普通页面和高级控制台的视觉区分。

验收：

- 不是只换皮肤。
- 信息密度可控。
- 主动作、次动作、危险动作一眼可分。

### 4.4 内容设计和术语系统

交付：

- 用户词表。
- 高级词表。
- 页面标题、副标题、按钮、错误提示、空状态文案。
- 能力状态文案：可用、计划中、不可用、需要配置。

验收：

- 不把未来能力写成已上线。
- 错误提示给具体下一步，不只显示异常字符串。

### 4.5 未来产品形态蓝图

交付：

- 本地产品、Docker 产品栈、桌面封装、SaaS 的入口关系图。
- 登录 / 无登录、本地 / 远端数据、同步 / 不同步的状态模型。
- 数据治理页面和远端服务的长期演进图。

验收：

- 当前本地优先承诺不被破坏。
- 远端同步、远端备份、远端删除都必须显式设计 consent 和状态。

### 4.6 工程落地包

交付：

- 页面级实现优先级。
- 组件规格和状态表。
- 设计 token。
- 响应式规则。
- 与现有 `apps/web` 组件的映射。
- 需要删除或下沉的旧入口清单。

验收：

- 工程团队可以分阶段实现。
- 不需要保留旧设计的过渡补丁。
- 废旧测试、废旧文档和误导入口有明确删除计划。

## 5. 建议的设计范围和优先级

### P0：先重做入口和主流程

- 首页 / 总览变成“开始工作”。
- 任务创建和启动成为首屏主动作。
- 应用选择从技术清单变成场景选择。
- 素材导入与任务创建串成一条路径。
- 高级控制面整体下沉。

### P1：重做任务运行和结果体验

- 任务状态、当前焦点、失败恢复、暂停恢复、预算和结果产物重新设计。
- 用户应能回答：任务在做什么、卡在哪里、我能点什么、结果在哪里。

### P2：重做设置、数据和发布边界

- provider 设置、模型选择、预算、工作区、权限合并成可理解设置。
- 数据位置、备份、恢复、删除预览形成数据管理页。
- 发布模式和未来 SaaS 不再只是矩阵，而是产品模式选择和支持边界。

### P3：重做高级工具区

- Prompt、MCP、评测、观测、协作、训练合并进高级模式。
- 高级模式可强大，但不要成为普通用户默认入口。

## 7. 设计团队选择建议

优先找有以下经验的团队：

- 做过开发者工具、AI 工作台、复杂 SaaS、数据平台或本地优先软件。
- 能做信息架构和交互，不只是视觉包装。
- 能处理多角色、多权限、多状态和长任务运行。
- 能写产品文案和术语系统。
- 能交付工程可落地的组件规格。

不建议找只擅长营销官网或纯视觉包装的团队。这个项目的核心问题是复杂工作流的产品化，不是首页好不好看。

## 8. 下一步建议

1. 先内部冻结产品一句话和首批目标用户。
2. 整理当前关键页面截图和 5 分钟首次任务录屏。
3. 写功能真相表，明确可用、计划中、不可承诺。
4. 按本文件的 briefing 包结构补齐材料。
5. 让设计团队先交信息架构和关键流程原型，再进入视觉设计。
6. 工程实现时直接替换旧入口，不做旧控制台上的渐进补丁。
