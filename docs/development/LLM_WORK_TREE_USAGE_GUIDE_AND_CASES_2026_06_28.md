# LLM 工作树使用指南与案例（2026-06-28）

## 文档定位

- 文档状态：Accepted as agent-facing guidance
- 来源：用户关于“LLM 控制方面重做”和“工作树应该这样用”的工作笔记。
- 范围：只定义 LLM 如何理解、选择和使用工作树；不新增 runtime 状态，不修改工具协议，不把本文写成新的硬控制器。
- 关联入口：

  - `docs/development/ROLLING_FRONTIER_WORK_TREE_RESOLUTION_2026_06_27.md`

本文把工作树重新定位为 LLM 的上下文卫生工具。工作树不是为了强迫模型按固定流程行动，而是帮助模型把临时探索、局部证据、失败尝试和重复性工作隔离在合适的工作节点里，让父节点只保留有用结论、证据和下一步判断。

## 核心判断

1. 工作树的首要作用是清理无效上下文，而不是制造任务仪式。
2. LLM 只需要知道工作树工具能做什么、什么时候值得用、使用后应该带回什么信息。
3. 不应强制 LLM 把工作树套到所有任务上。短小、单步、上下文干净的任务可以直接完成。
4. 提升任务质量主要靠任务定义、证据要求和高质量案例，而不是堆叠规则。
5. runtime hints、ready-set、delivery readiness 只提供线索或边界，不替 LLM 决定语义顺序。
6. 安全、预算、不可逆操作、对外发布、真实付费调用仍是硬边界；普通规划、探索和局部状态优先交给 LLM 自主判断。
7. 废旧节点、失败尝试和不再采用的路线要在摘要中明确标记为废弃或只作为经验保留，避免旧设计重新污染父节点。

## LLM 应理解的工作树功能

| 功能 | 用法 | 设计意义 |
| --- | --- | --- |
| 子工作节点 | 为一个局部操作、尝试、方向或重复项创建独立工作空间 | 把临时细节留在子节点，父节点只拿回摘要 |
| 父节点回收 | 子节点完成后向父节点返回结论、证据、失败经验和剩余风险 | 避免父节点被搜索记录、编辑过程和中间草稿淹没 |
| 兄弟节点 | 把多个都要完成的方面拆成同级节点 | 便于并行调查、比较和最终综合 |
| `dependsOn` 控制边 | 当前节点需要等待另一个节点结果时使用 | 表达硬依赖，防止还没拿到前置证据就交付 |
| `relationIds` 信息边 | 节点之间只是共享背景、参考或可复用经验时使用 | 传递信息，不阻塞调度 |
| `expectedEvidence` / `producedEvidenceRefs` | 记录一个节点需要什么证据、已经产出什么证据 | 把“是否真的做过”变成可审计事实 |
| `runtime_hints` | 读取当前节点、开放前沿和交付就绪线索 | 帮助选择下一步，不覆盖任务目标和现场判断 |
| Fork / 并行 child | 多个相对独立的 child 都值得推进且资源允许时使用 | 加速调查和比较，但并发槽只是资源租约 |
| 记忆 / 工具写入 | 把长期有价值的结论、证据和失败经验沉淀到正式记忆或工件 | 让后续窗口不用重新经历完整上下文 |

## 什么时候应该使用工作树

### 情况 1：一组操作结束后只需要部分信息

典型场景：查资料、批量读文件、局部改代码、跑一组验证。

使用方式：

1. 在子节点里完成高噪声操作。
2. 子节点保留搜索路径、阅读记录、失败命令和中间草稿。
3. 返回父节点时只带回：关键结论、证据引用、修改点、验证结果、风险。

示例：

> 我需要确认某个 provider 路由问题。先进入子节点读取配置、日志和相关测试；父节点只需要知道根因、涉及文件、验证命令和是否还残留风险。

父节点应收到：

- 根因：候选模型被 `requiredContextWindow` 过滤，而不是 provider key 缺失。
- 证据：配置文件路径、测试名、日志片段位置。
- 处理：改哪一层、跑了什么测试。
- 风险：只覆盖 LongCat/DeepSeek，其他 provider 还未复测。

### 情况 2：任务有多个方面，所有方面都要做

典型场景：大范围审计、一系列修复、资料包整理、发布门禁检查。

使用方式：

1. 父节点定义总目标和最终合成标准。
2. 每个方面一个 child，例如 docs、runtime、tests、evaluation、release。
3. 父节点不直接塞所有细节，只收每个 child 的结论表。

示例结构：

```text
root: 判断当前发行包是否可公开试用
├── child: 产品启动路径核查
├── child: 数据隐私和出机边界核查
├── child: Docker / Windows 封装核查
├── child: 文档与发布手册核查
└── child: 验证命令和证据汇总
```

父节点最终合成：

- 哪些能力已经可承诺。
- 哪些只是预览。
- 哪些不能写成已完成。
- 发布前必须补的门禁。

### 情况 3：任务有多个步骤，步骤有关联但不是同一个上下文

典型场景：软件工程、科学研究、产品调研、长文写作。

使用方式：

1. 把步骤拆成节点，避免一个窗口同时背负全部历史。
2. 硬前置关系用 `dependsOn`。
3. 只是共享资料或经验用 `relationIds`。
4. 后一步只继承前一步的摘要、证据和关键决策。

示例结构：

```text
root: 完成某个 runtime 语义调整
├── child A: 现状与入口定位
├── child B: 设计收口
│   dependsOn: A
├── child C: 代码修改
│   dependsOn: B
├── child D: 测试与废旧断言清理
│   dependsOn: C
└── child E: 文档与目录索引同步
    dependsOn: C
    relationIds: B, D
```

这样能保留工程顺序，又不会让每个节点都携带所有文件阅读细节。

### 情况 4：任务有难度，但可以先做局部尝试

典型场景：探索型研究、创造类工作、复杂 bug 隔离、未知技术路线。

使用方式：

1. 在父节点写清楚“这是尝试，不是最终路线”。
2. 子节点只验证一个假设。
3. 成功则把可复用结论带回父节点；失败则带回失败原因和避坑经验。
4. 失败子节点不应继续污染主路线。

示例：

```text
root: 降低长任务 prompt 控制感
├── child: 尝试只改 response_requirements
├── child: 尝试只改 runtime_hints 展示
└── child: 比较两条路线对测试和评测的影响
```

父节点保留的不是完整尝试过程，而是“哪条路线更稳、为什么、需要删除哪些旧断言”。

### 情况 5：方向不确定，多个方向都值得试

典型场景：前沿科研、开放产品设计、复杂架构选择。

使用方式：

1. 每个候选方向一个子节点。
2. 每个子节点独立产出同一种比较材料：收益、成本、风险、证据、淘汰条件。
3. 父节点只做比较和选择，不把某个方向的口径悄悄当成全局默认。

示例结构：

```text
root: 选择长程任务控制策略
├── child: 规则式控制
├── child: 启发式 runtime hints
├── child: 案例学习 + 任务定义
└── child: 混合方案的最低控制边界
```

父节点最终应该明确：

- 采用什么。
- 放弃什么。
- 放弃项为什么不保留兼容层。
- 哪些旧测试或旧文档需要删除或降级。

### 情况 6：大量重复性工作

典型场景：时间线调查、客服批量回复、逐文件审查、逐供应商比较。

使用方式：

1. 每个重复项一个节点，保持统一输出模板。
2. 父节点收表格或归纳，不接收每个重复项的完整过程。
3. 重复项之间如果发现共性，父节点可以新建一个“共性分析”节点。

示例：

```text
root: 梳理 12 个事件的真实时间线
├── child: 事件 1 核对
├── child: 事件 2 核对
├── child: ...
└── child: 共性矛盾与可信度分层
```

每个事件节点返回：

| 字段 | 内容 |
| --- | --- |
| 时间 | 明确日期或时间范围 |
| 来源 | URL、文件、记录 ID |
| 可信度 | 高 / 中 / 低 |
| 矛盾 | 与哪些来源冲突 |
| 父节点可用结论 | 一句话 |

### 情况 7：工作目标暂不明确

典型场景：用户只给一个方向、任务很开放、需求会变化、早期探索。

使用方式：

1. 先进入探索子节点，而不是把所有猜测留在父节点。
2. 子节点负责澄清目标、列可行路径、排除无效方向。
3. 父节点只保留“可执行目标版本”和“仍需用户确认的问题”。

示例：

```text
root: 做一个研究报告
└── child: 目标澄清与材料盘点
```

子节点返回：

- 建议目标：面向投资判断的行业进展报告。
- 已确认材料：3 份访谈、2 个政策文件。
- 不确定项：是否需要财务模型。
- 下一步：按“表内事实 / 行业假设 / 待验证”建三个子节点。

这类用法能让父节点保持干净。即使任务方向后来变化，旧探索的无效内容也不会挤占主上下文。

## 组合型使用案例

### 组合案例 A：大范围代码修复

任务：修复一个 runtime 恢复链 bug，并确保文档不再指向旧语义。

建议结构：

```text
root: 修复恢复链 bug 并同步 repo truth
├── child: 复现和根因定位
├── child: 当前协议和文档口径核查
├── child: 最小代码修改
├── child: 废旧测试删除或改写
├── child: 回归验证
└── child: DIRECTORY_REFERENCE 同步
```

用法要点：

- 复现节点可以保留大量日志，但父节点只接收根因链。
- 文档核查节点要指出旧设计是否废弃，不能为了兼容旧设计留双口径。
- 测试节点要删除废旧路线断言，不能只给新语义补一层兼容测试。
- 索引节点负责把新真相写入 `docs/DIRECTORY_REFERENCE.md`。

父节点最终交付：

- 改动文件。
- 删除或改写的旧测试。
- 验证命令和结果。
- 未完成项和阻塞项。

### 组合案例 B：开放研究任务

任务：研究一种新技术路线是否适合本项目。

建议结构：

```text
root: 判断技术路线是否适合本项目
├── child: 外部资料检索
├── child: 项目内约束核对
├── child: 候选方案 A
├── child: 候选方案 B
├── child: 失败路线和淘汰原因
└── child: 推荐结论与证据表
```

用法要点：

- 外部资料检索节点只返回来源、时间、关键 claim 和矛盾点。
- 项目内约束节点只返回当前 repo truth，不把行业假设当成代码事实。
- 候选方向节点使用同一比较维度，方便父节点综合。
- 失败路线要保留淘汰原因，避免后续 agent 重复走回头路。

### 组合案例 C：长程产品发行核查

任务：判断当前版本能否发布给外部用户。

建议结构：

```text
root: 外部发布准备度判断
├── child: 用户入口和首次成功路径
├── child: 安装 / 启动 / Docker 依赖
├── child: provider key 和出机边界
├── child: 数据治理和删除边界
├── child: release package 与 checksum
├── child: 公开文档口径
└── child: 发布决策汇总
```

用法要点：

- 每个节点都要区分“已实现”“预览可用”“计划中”“不可承诺”。
- 真实发布证据不能用 smoke 或估算冒充。
- 父节点只做发布判断，不保留每个检查项的全部命令输出。

### 组合案例 D：大量材料整理后写作

任务：把一批访谈、政策和历史材料整理成报告。

建议结构：

```text
root: 产出可引用报告
├── child: 材料清点和来源可信度
├── child: 观点提取
├── child: 案例提取
├── child: 时间线整理
├── child: 矛盾和缺口
└── child: 报告写作
```

用法要点：

- 材料节点保留原始摘录，父节点只保留引用索引。
- 写作节点只继承必要论点、案例和引用，不重新背全部材料。
- 如果报告目标变化，新写作节点可以从父节点重新出发，不必携带废稿全文。

## 给 LLM 的简短提示范式

以下文本适合放进 agent-facing prompt 或案例库，而不是作为每轮硬规则重复灌入：

```text
工作树用于清理上下文。任务简单时直接完成；当某段工作会产生大量临时细节、失败尝试、重复项或候选方向时，先把它放进子工作节点。子节点完成后，只把父节点真正需要的结论、证据、风险和下一步带回。工作树提示只是辅助线索，不替你决定语义顺序；安全、预算、不可逆操作和用户明确审批仍是硬边界。
```

## 好的父节点摘要长什么样

子节点返回父节点时，优先使用这种结构：

```text
结论：
- ...

证据：
- 文件 / URL / 命令 / 记录 ID：说明它证明什么。

已废弃路线：
- 路线：为什么废弃，后续不要继续沿用什么假设。

剩余风险：
- ...

建议下一步：
- ...
```

父节点不需要：

- 完整搜索过程。
- 完整日志。
- 每个失败命令的全部输出。
- 未采用方案的长篇论证。
- 子节点内部临时草稿。

## 反例

| 反例 | 问题 | 应改成 |
| --- | --- | --- |
| 每个简单任务都先建树 | 工作树变成仪式，增加无效上下文 | 简单任务直接答复或直接修改 |
| 子节点把所有搜索结果复制回父节点 | 父节点仍被污染 | 子节点只带回来源表和关键 claim |
| 父节点同时追踪 5 个候选方向细节 | 候选路线互相污染 | 每个候选方向独立 child，父节点只比较 |
| 为旧设计保留兼容解释 | 后续 agent 会继续走旧路线 | 标明旧设计废弃，删除或降级旧测试 |
| 把 `runtime_hints` 当命令 | LLM 被控制器牵走 | 把 hints 当未解决主题摘要，结合任务现场判断 |
| 用 Fork 替代语义拆分 | 并发槽变成任务设计 | 先由 LLM 决定拆分，再让 scheduler 管资源 |
