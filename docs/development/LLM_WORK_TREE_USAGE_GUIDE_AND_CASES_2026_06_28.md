本文把工作树定位为 LLM 的上下文卫生工具。它不是为了强迫模型执行固定流程，而是让模型把搜索、局部试错、重复项、候选路线、编辑过程和失败尝试隔离在合适节点里，让父节点保持高层视角和干净上下文。

## 核心判断

1. 工作树的首要作用是清理无效上下文，而不是制造任务仪式。
2. LLM 应清楚知道工作树工具能做什么、什么时候值得用、用后应该把哪些有用信息带回父节点。
3. 不应强制 LLM 为了形式建树；但也不能把“不强制建树”理解成所有执行都堆在 root。
4. 根节点应该只完成工作流程控制方面的任务；非叶子节点的任务都应该是控制任务流程和思考，叶子节点才执行。
5. 提升任务质量主要靠任务定义、证据要求和高质量案例；工作树使用案例必须进入 prompt，而不只是停在文档里。
6. LLM 应被要求做更多事情：主动重估目标、推进下一步、隔离噪声、比较候选路线、回收有用信息，而不是只生成阶段性报告。
7. 对 LLM 的控制应尽量靠启发和案例，不靠厚规则、硬模板或状态堆叠。
8. 安全、预算、不可逆操作、对外发布、真实付费调用仍是硬边界；普通规划、探索和局部状态优先交给 LLM 自主判断。
9. 废旧节点、失败尝试和不再采用的路线要标明废弃原因，避免旧设计重新污染父节点。
10. 父节点负责清理已经不再需要的子节点；多个 seed 占位子节点已被真实 completed child 覆盖时，应批量 skip/prune，不能让旧占位节点永久阻塞 root 收束。

## LLM 应理解的工作树功能

| 功能 | 用法 | 设计意义 |
| --- | --- | --- |
| `currentNodeId` / `Working_Node` | 识别当前正在工作的节点 | 防止 LLM 忘记自己是在 root、child 还是 leaf |
| `WorkContextStack` | 读取当前执行栈、父子关系和最近 child 回收信息 | 让父节点能保持高层视角，leaf 能专注执行 |
| 子工作节点 | 为局部操作、尝试、候选方向、重复项或执行过程创建独立空间 | 把过程噪声留在子节点；父节点只接收有用信息 |
| 父节点回收 | child 完成后返回结论、证据、引用、废弃路线和风险 | 让父节点负责综合判断，而不是背完整日志 |
| 兄弟节点 | 把多个都要完成的方面拆成同级节点 | 支持并行调查、比较和最终综合 |
| `dependsOn` 控制边 | 当前节点必须等待另一个节点结果时使用 | 表达硬依赖，防止前置证据缺失就交付 |
| `relationIds` 信息边 | 节点之间只是共享背景、参考或经验时使用 | 传递信息，不阻塞调度 |
| Fork / 并行 child | 多个相对独立的 child 都值得推进且资源允许时使用 | 加速调查和比较；并发槽只是资源租约 |
| 记忆 / 文件 / 信息边引用 | 把长期有价值的信息或大型产物作为引用带回 | “带回”不等于手写完整摘要，引用也是有用信息 |
| `runtime_hints` | 读取当前节点、开放前沿和交付就绪线索 | 只是辅助线索，不覆盖任务目标和现场判断 |
| `expectedEvidence` / `producedEvidenceRefs` | 记录某些节点需要和已经产出的证据 | 属于项目现有审计字段；不应变成 LLM 的新硬模板 |

## 高层视角与重新审视

工作树是否有效，关键不在“建了几个节点”，而在 root 和非叶子节点是否持续保持高层视角。

LLM 应在这些时点重新审视任务：

1. 开始执行前：当前任务到底要交付什么，哪些方面都必须完成，哪些只是候选路线。
2. 每轮重要工具批次后：新证据是否改变了问题定义、拆分结构或优先级。
3. child 完成后：父节点自己判断下一步，而不是机械接受 child 的“建议下一步”。
4. 准备交付前：是否只是阶段材料，是否还有未闭合节点、证据缺口或废弃路线未标明。

父节点要问的问题：

- 这个任务的总目标是否仍然正确？
- 当前节点是不是应该继续执行，还是应该拆给 leaf？
- 哪些过程信息应留在 child，哪些有用信息要带回？
- 哪些路线已经失败，后续 agent 不应再沿用？
- 当前交付是否有真实工具/文件/来源证据支撑？
- 是否存在已被真实 completed child 覆盖的 seed 占位子节点？如果有，父节点应清理它们。

父节点在 child 完成后必须显式选择：

1. 继续开 leaf：还有明确证据缺口、实现缺口或验证缺口。
2. 关闭/清理 child：child 已完成、失败、重复、过时或已被其他 child 覆盖。
3. 最终交付：所有 child 都是 terminal（completed / failed / skipped），交付合同已满足，且没有未命名 blocker。

## 什么时候应该使用工作树

### 情况 1：一组操作结束后只需要部分有用信息

典型场景：查资料、批量读文件、局部改代码、跑一组验证。

使用方式：

1. 在子节点里完成高噪声操作。
2. 子节点保留搜索路径、阅读记录、失败命令和中间草稿。
3. 回父节点时带回关键结论、证据引用、文件引用、记忆节点引用、废弃路线和风险。

### 情况 2：任务有多个方面，所有方面都要做

典型场景：大范围审计、一系列修复、资料包整理、发布门禁检查。

使用方式：

1. 父节点定义总目标和最终合成标准。
2. 每个方面一个 child，例如 docs、runtime、tests、evaluation、release。
3. 每个 child 可继续拆 leaf 执行具体搜索、编辑或验证。
4. 父节点只综合各 child 的有用信息。

### 情况 3：任务有多个步骤，步骤有关联但不是同一个上下文

典型场景：软件工程、科学研究、产品调研、长文写作。

使用方式：

1. 把步骤拆成节点，避免一个窗口同时背负全部历史。
2. 硬前置关系用 `dependsOn`。
3. 只是共享资料或经验用 `relationIds`、记忆引用或文件引用。
4. 后一步只继承前一步的有用信息和关键决策。

### 情况 4：任务有难度，但可以先做局部尝试

典型场景：探索型研究、创造类工作、复杂 bug 隔离、未知技术路线。

使用方式：

1. 父节点写清楚“这是尝试，不是最终路线”。
2. 子节点只验证一个假设。
3. 成功则带回可复用结论和证据；失败则带回失败原因和避坑经验。
4. 失败子节点不继续污染主路线。

### 情况 5：方向不确定，多个方向都值得试

典型场景：前沿科研、开放产品设计、复杂架构选择。

使用方式：

1. 每个候选方向一个子节点。
2. 每个子节点独立产出同一种比较材料：收益、成本、风险、证据、淘汰条件。
3. 父节点只做比较和选择，不把某个方向的口径悄悄当成全局默认。

### 情况 6：大量重复性工作

典型场景：时间线调查、客服批量回复、逐文件审查、逐供应商比较。

使用方式：

1. 每个重复项一个子节点或 leaf。
2. 父节点收表格、索引或归纳，不接收每个重复项的完整过程。
3. 重复项之间如果发现共性，父节点可以新建“共性分析”节点。

### 情况 7：工作目标暂不明确

典型场景：用户只给一个方向、任务很开放、需求会变化、早期探索。

使用方式：

1. 先进入探索子节点，而不是把所有猜测留在父节点。
2. 子节点负责澄清目标、列可行路径、排除无效方向。
3. 父节点只保留“可执行目标版本”和“仍需用户确认的问题”。

这些情况应该互相嵌套使用，而不是被理解成互斥分类。

## 组合型使用案例

组合型案例必须体现多层任务分解：root 管总目标，middle 节点管方面或阶段，leaf 节点执行具体动作。

### 组合案例 A：大范围代码修复

```text
root: 修复恢复链 bug 并同步 repo truth
├── child: 复现和根因定位
│   ├── leaf: 读取失败日志和窗口工件
│   └── leaf: 最小复现
├── child: 当前协议和文档口径核查
├── child: 代码修改
│   ├── leaf: 修改 runtime
│   └── leaf: 删除废旧兼容路径
├── child: 测试与废旧断言清理
├── child: 回归验证
└── child: DIRECTORY_REFERENCE 同步
```

父节点最终合成：改动文件、删除或改写的旧测试、验证命令和结果、未完成项。

### 组合案例 B：开放研究任务

```text
root: 判断技术路线是否适合本项目
├── child: 外部资料检索
│   ├── leaf: 学术来源
│   ├── leaf: 官方文档
│   └── leaf: 产业报告
├── child: 项目内约束核对
├── child: 候选方案 A
├── child: 候选方案 B
├── child: 失败路线和淘汰原因
└── child: 推荐结论与证据表
```

父节点要明确“来源事实 / 研究判断 / 工作假设 / 待验证空白”，不能把行业假设写成项目事实。

### 组合案例 C：真实任务审计

```text
root: 判断一次真实 LLM 任务是否可信
├── child: prompt 编译结果核查
├── child: LLM 行为记录核查
│   ├── leaf: rounds 与 toolExecutions
│   ├── leaf: assistant 自述与真实工具次数差异
│   └── leaf: work-tree directive / currentNodeId
├── child: 交付物质量核查
└── child: 结论与改进项
```

这个案例对应储能研究类任务：不能只看最终报告，要看系统派生的 prompt、response、toolExecutions、window-execution 和 behavior-record 工件。

### 组合案例 D：大量材料整理后写作

```text
root: 产出可引用报告
├── child: 材料清点和来源可信度
├── child: 观点提取
├── child: 案例提取
├── child: 时间线整理
├── child: 矛盾和缺口
└── child: 报告写作
```

材料节点保留原始摘录，父节点只保留引用索引；如果报告目标变化，新写作节点可以从父节点重新出发，不携带废稿全文。

## 给 LLM 的简短提示范式

以下文本适合放进 agent-facing prompt 或案例库，而不是作为厚规则重复灌入：

```text
工作树用于清理上下文。root 和非叶子节点负责高层视角、流程控制、方向重估和信息合并；叶子节点负责具体执行。当执行会产生搜索记录、命令输出、编辑过程、失败尝试、重复项或候选方向时，把执行放进合适的子节点或 leaf。child 完成后带回父节点需要的有用信息、证据/文件/记忆引用、已废弃路线和风险；父节点自己重新审视任务并决定下一步。
```

## 好的父节点回收长什么样

子节点回父节点时，优先使用这种结构：

```text
结论：
- ...

有用信息与引用：
- 文件 / URL / 命令 / 记录 ID / 记忆节点 / 信息边：说明它证明什么。

已废弃路线：
- 路线：为什么废弃，后续不要继续沿用什么假设。

剩余风险：
- ...
```

父节点清理废旧子节点时，优先使用这种结构：

```text
<work-node-prune nodeIds="seed-question,seed-constraints,seed-evidence">
这些 seed 占位节点没有独立产出，且已经被 completed child report-synthesis 的报告、来源表和矛盾分析覆盖；保留它们只会阻塞 root 收束。
</work-node-prune>
```

如果要清理的节点下面已经有 leaf，父节点必须先确认 leaf 的结果已被吸收，再清理父节点：

```text
<work-node-prune nodeId="obsolete-research-branch" confirmChildren="true">
确认该分支下 leaf-a / leaf-b 的证据与失败原因已经进入父节点摘要和最终报告；该分支现在是过时路线，可以清理，避免继续污染父节点。
</work-node-prune>
```

如果子树里还有未完成 leaf，不能清理；应先进入 leaf 完成、失败，或由父节点确认它被其他结果覆盖后再处理。

父节点不需要：

- 完整搜索过程。
- 完整日志。
- 每个失败命令的全部输出。
- 未采用方案的长篇论证。
- 子节点内部临时草稿。
- child 替父节点写好的“建议下一步”。

## 反例

| 反例 | 问题 | 应改成 |
| --- | --- | --- |
| 为每个动作机械建树 | 工作树变成仪式，增加无效上下文 | 先判断当前节点职责；执行会产生过程噪声时再把执行放进子节点或 leaf |
| 用“不强制建树”当作 root 直接执行所有工作的理由 | root 被搜索、编辑和失败尝试污染 | root 保持高层视角，具体执行进入 child / leaf |
| 子节点把所有搜索结果复制回父节点 | 父节点仍被污染 | 子节点带回有用信息和引用，原始过程留在子节点 |
| 父节点同时追踪 5 个候选方向细节 | 候选路线互相污染 | 每个候选方向独立 child，父节点只比较 |
| child 返回“建议下一步”并让父节点照做 | 父节点被局部视角带跑 | child 返回证据、风险和废弃路线；父节点重新审视后决策 |
| seed 占位节点已被真实 child 覆盖但不清理 | 报告已经产出，root 仍因 pending child 无法收束 | 父节点用 `work-node-prune nodeIds="..."` 批量清理无后代占位节点；有 leaf 的子树需 `confirmChildren="true"` |
| 为旧设计保留兼容解释 | 后续 agent 会继续走旧路线 | 标明旧设计废弃，删除或降级旧测试 |
| 把 `runtime_hints` 当命令 | LLM 被控制器牵走 | 把 hints 当未解决主题摘要，结合任务现场判断 |
| 用 Fork 替代语义拆分 | 并发槽变成任务设计 | 先由 LLM 决定拆分，再让 scheduler 管资源 |

## LLM 行为记录器要求

后续真实任务不能只依赖模型在最终报告中自述“我查了什么”。系统应由 runtime 派生稳定行为记录：

- 输入：compiled prompt、request、response、round summaries、toolExecutions、runtime metrics。
- 输出位置：`.yggdrasil/state/llm/behavior-records/{invocationId}.json`。
- 按任务索引：`.yggdrasil/state/llm/behavior-records/by-task/task_{taskId}.json`。
- 记录内容：rounds、工具执行明细、真实工具次数、assistant 输出里的 work-tree directive、prompt 是否包含工作树案例、assistant 自述工具次数与真实工具次数的差异。
- 原则：记录器是系统事实，不信任模型自述；记录失败只降级为 warning，不阻断主任务。
