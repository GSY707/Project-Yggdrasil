# 世界树计划 · 真实用户环境验证计划

> 记录日期：2026-04-30
> 目标：验证基于世界树计划搭建的 Agent 在真实用户环境下是否好用、配置是否正确、响应速度是否达标，以及是否在关键任务上优于主流竞品。

---

## 1. 需要回答的结论

本轮验证必须分别回答下面 4 个问题，不能混成一次泛化测试：

1. **真实用户是否能顺利完成任务？**
2. **真实环境中的配置是否稳定、可诊断、可恢复？**
3. **端到端响应速度是否足以支撑日常使用？**
4. **在相同任务和相近模型条件下，世界树 Agent 是否比竞品更强？**

其中第 4 个问题不以“单次生成更好看”为标准，而以长期任务、跨会话连续性、暂停恢复、人工返工量和可观测性为主。

## 3. 验证原则

### 3.1 公平性原则

- 同一任务包必须在同一材料、同一时间盒、同一权限边界下执行。
- 如条件允许，尽量统一模型家族和上下文材料，避免把模型差异误判为 Agent 差异。
- 竞品对比建议采用盲评，评审只看结果与过程记录，不先看系统名称。

### 3.2 真实性原则

- 至少 50% 的任务必须跨会话执行，否则测不到世界树的长期任务优势。
- 至少 20% 的任务必须包含异常或中断，否则测不到 safe-stop / resume 的真实价值。
- 至少一组环境必须故意引入依赖降级或配置缺失，验证错误可诊断性。

### 3.3 分层原则

- 配置正确性与基础门禁先跑自动化，再进入人工测试。
- 性能数据单独采集，不混在主观问卷里。
- 用户体验结论以任务完成和返工成本为主，不以“感觉聪明”代替。

## 5. 环境矩阵

建议先跑核心矩阵，再视目标用户增加扩展矩阵。

| 环境 ID | 环境描述 | 目的 | 必须观察的点 | 通过标准 |
|--------|----------|------|--------------|----------|
| E1 | Windows 11 本机，最小依赖，`coordination=auto` | 验证默认开发机上手路径 | 首次启动、依赖探测、回退提示 | 首次任务可完成，无阻塞误配 |
| E2 | Windows 11 本机，完整 infra | 验证正式本地联调主路径 | Redis / NATS / DB / Web / Runtime 联通 | 关键命令全通过 |
| E3 | Windows 11 本机，Redis 不可达 | 验证 coordination fallback | 是否自动回退、是否有明确提示 | 任务可继续，日志可解释 |
| E4 | WSL2 Ubuntu 或干净 Linux 环境，完整 infra | 验证跨环境一致性 | 安装、脚本、端口、路径差异 | 主链路通过率不低于 E2 |
| E5 | Windows 11 本机，`auditLevel=strict` | 验证重审计场景成本与可用性 | 首响延迟、工件体积、链路完整性 | 能跑通且性能退化可解释 |
| E6 | Windows 11 本机，`auditLevel=lean` | 验证轻审计场景下速度收益 | 首响时间、总耗时、可观测性折损 | 比 strict 明显更快 |

如果目标发布范围包含 macOS，应增加 E7：macOS + 完整 infra。

## 7. 指标体系

### 7.1 客观指标

| 维度 | 指标 | 说明 |
|------|------|------|
| 任务结果 | 任务完成率 | 是否在时间盒内达到验收标准 |
| 任务结果 | 首次有效结果时间 | 从开始到第一次可用输出的秒数 |
| 任务结果 | 总完成时间 | 从开始到验收结束的秒数 |
| 过程成本 | 人工接管次数 | 用户必须主动纠偏或重定向的次数 |
| 过程成本 | 用户澄清回合数 | 仅统计围绕需求边界与权限边界的必要提问次数 |
| 过程成本 | 人工编辑时长 | 用户为拿到可接受结果投入的额外分钟数 |
| 连续性 | 跨会话连续完成率 | 第二次进入时是否延续上轮上下文，而非重做 |
| 连续性 | pause/resume 成功率 | 安全暂停和恢复是否保持一致性 |
| 配置质量 | 环境矩阵通过率 | 核心矩阵通过占比 |
| 配置质量 | 配置问题定位时长 | 从发现到确认根因所需时间 |
| 性能 | P50 / P95 首次有效输出时间 | 用户主观体感最强的时延指标 |
| 性能 | P50 / P95 端到端任务时间 | 完整交付速度 |

### 7.2 人工评审指标

| 维度 | 评分范围 | 判定依据 |
|------|----------|----------|
| 输出质量 | 0-5 | 是否满足验收、是否存在明显错误 |
| 过程稳定性 | 0-5 | 是否频繁迷失、循环、重复劳动 |
| 配置可诊断性 | 0-5 | 出错时能否快速知道哪里错、怎么修 |
| 继续使用意愿 | 0-5 | 用户是否愿意在真实工作中继续用 |

### 7.3 评分方法

建议先保留原始观测值，再归一化出 5 个分项分数，最后得到加权总分。

| 分项 | 权重 | 评分方式 |
|------|------|----------|
| `task_outcome_score` | 40% | 是否完成验收 + 输出质量 |
| `human_effort_score` | 20% | 接管次数、编辑时长、返工量 |
| `continuity_recovery_score` | 20% | 跨会话延续、pause/resume、异常恢复 |
| `response_speed_score` | 10% | 相对同批次中位数的速度表现 |
| `config_quality_score` | 10% | 环境通过率、误配数、定位难度 |

**推荐归一化规则：**

- `task_outcome_score`
  - 100：时间盒内通过验收，且输出质量 ≥ 4
  - 70：完成主要目标，但仍需中等人工修整
  - 40：只完成部分目标
  - 0：失败或阻塞
- `human_effort_score`
  - 100：无需接管，人工编辑 ≤ 5 分钟
  - 80：轻微接管，人工编辑 ≤ 15 分钟
  - 60：中度接管，人工编辑 ≤ 30 分钟
  - 30：重度接管，人工编辑 ≤ 60 分钟
  - 0：基本依赖人工重做
- `continuity_recovery_score`
  - 100：恢复后直接延续，无重复劳动和状态错乱
  - 70：可恢复，但需要人工重新校正部分上下文
  - 30：恢复后大量重复劳动
  - 0：无法恢复或恢复结果不可信
- `response_speed_score`
  - 100：与同批次最佳结果持平
  - 85：比最佳结果慢不超过 15%
  - 70：比最佳结果慢不超过 30%
  - 50：比最佳结果慢不超过 50%
  - 0：比最佳结果慢超过 50%
- `config_quality_score`
  - 100：无配置问题或 5 分钟内可定位
  - 80：有轻微误配，但不阻塞
  - 50：存在需要人工查阅多处文档的误配
  - 0：阻塞级误配或根因难以定位

**加权总分公式：**

```text
weighted_total_score
= 0.4 * task_outcome_score
+ 0.2 * human_effort_score
+ 0.2 * continuity_recovery_score
+ 0.1 * response_speed_score
+ 0.1 * config_quality_score
```

## 8. “比别人家强”的判定门槛

只有同时满足下面条件，才建议对外宣称“在当前目标场景下更强”：

1. 加权总分比主要竞品高 **10 分** 以上。
2. 跨会话长任务的平均分 **不能低于** 最强竞品。
3. 恢复类任务的成功率至少 **90%**。
4. 核心环境矩阵通过率至少 **95%**。
5. 首次有效结果时间的 P50 不能比最强竞品慢 **15%** 以上。

如果只在快任务上赢、但在跨会话或恢复任务上输，不应得出“整体更强”的结论。

在正式跑真实用户前，至少保证下面 8 段链路能被记录：

1. 任务创建到首个状态变化

5. 模型调用耗时

每段都要区分：

- 冷启动
- 热启动
- `auditLevel=strict`
- `auditLevel=default`
- `auditLevel=lean`

## 10. 执行节奏

### 第 1 周：基线与材料冻结

- 跑自动化门禁和环境矩阵
- 冻结任务包、仓库版本、研究语料版本
- 检查埋点字段是否齐全
- 先做 2 到 3 次内部试跑，修掉阻塞性误配

### 第 2 周：内部用户与首轮竞品对比

- 5 到 8 名内部用户执行任务包
- 对照组同步执行相同任务
- 收集原始分数、录屏、日志、trace、工件
- 汇总前 5 个阻塞因素并分类归因

### 第 3 周：修复后复测

- 只修影响结论最大的前几项
- 用同一任务包完整复测
- 产出最终评分卡和 go / no-go 建议
