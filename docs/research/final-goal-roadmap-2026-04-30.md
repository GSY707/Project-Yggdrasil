# 世界树计划 · 通向最终目标的路线图（可执行草稿 v0.1）

> 最终目标：通用世界树 Agent + 一个初始原则 + 用户任务 -> 高质量完成任务；中间只在需求与权限边界上和用户对齐；运行发生在服务器侧，Agent 拥有自己的隔离资源。
>
> 本文档不是愿景陈列，而是把现有工程状态、真实用户验证计划和最终目标之间的路径收口成一条可执行路线。它仍然是草稿，但已经按“能否在当前仓库里继续推进”做过一轮可行性修正。

---

## 1. 路线设计原则

这条路线必须同时满足下面 6 个原则，否则就是不可执行的空路线：

1. 先证明结果，再扩能力。不能在“用户只给目标，系统能完成任务”尚未被验证前继续堆模块。
2. 先做窄路径闭环，再谈通用性。先把 1 到 2 条高价值路径做稳，再扩展到更多场景。
3. 所有阶段都必须可证伪。每一阶段都要有明确出口标准和 go / no-go 条件。
4. 服务器侧运行不是包装词，而是基础约束。隔离工作区、资源配额、恢复能力、审计链路都必须先落地。
5. 优化来源于评测和试跑，而不是主观感觉。任何“更聪明”的改动都要进回归或 A/B。
6. 不把最终目标误解成“什么都能做”。真正目标是“少澄清、少返工、高完成率、稳定可恢复”。

---

## 2. 为什么不能直接冲最终目标

如果直接按“补更多能力模块、补更多场景、补训练、补联网”推进，路线会失效，原因很具体：

1. 当前最核心的不确定性不是功能够不够，而是用户只给目标时系统到底能不能稳定交付。
2. 真实用户验证和内部试跑材料已经冻结，继续大改能力面会让“冻结版本”和“验证版本”再次分裂。
3. 服务器侧独立运行的核心不是多几个工具，而是隔离、恢复、调度、观测和长任务稳定性。
4. 自我进化、训练和多场景泛化，只有在基础 UX 和运行时稳定后才有意义；否则只是把噪音放大。

因此，路线必须采用 gate 方式推进，而不是功能清单方式推进。

---

## 3. 最终目标拆解

最终目标实际上由 5 个子目标组成，缺一项都不成立：

### G1. 目标接管

用户只描述目标和必要约束，系统可以自己完成任务拆解、执行、验证和收尾。

### G2. 长任务稳定

任务可以跨会话、跨重启、跨 safe-stop / resume 持续推进，而不是每次都重新解释上下文。

补充说明（2026-05-16）：G2 的完整形态不是“偶尔能 resume”，而是“记忆树作为持久主体，上下文窗口只是临时工作集”。理论上，只要单次 token 生成所需的工作集能够稳定装入当前窗口，任务就可以通过动态加载记忆、上下文压缩和窗口重启在多个窗口之间持续推进。这也是项目当前通往“伪无限上下文窗口”的正式定义。

### G3. 服务器侧独立执行

Agent 在自己的隔离资源里运行，拥有工作区、状态根、资源预算、工具链和审计链，而不是依附当前对话临时做事。

### G4. 场景泛化

系统不只会做单一路径任务，而是能在编码、研究、写作等若干高价值场景中保持稳定交付。

### G5. 自我优化闭环

系统能基于试跑、评测、错误和长期数据持续改进，但改进必须受门禁和回归保护。

---

## 4. 提示词成熟度分级

这里的“提示词水平”不是指文案好不好看，而是指 prompt 资产、编译链、few-shot、动态选择和评测回路的成熟度。

### P1. 固定规则层

- 目标：先把稳定规则从线性 system prompt 里拆出来。
- 资产：一个 generic PromptProfile，少量基础 SeedTemplate。
- 特征：能稳定表达 systemRole、behaviorGuidelines、toolPolicy、outputContract，但主要还是静态规则。
- 适用阶段：验证窄路径是否能交付。

### P2. 结构化编译层

- 目标：把稳定规则和运行时状态明确分层。
- 资产：完整 PromptProfile / SeedTemplate 字段，PromptCompiler 编译链，基础 few-shot。
- 特征：system 侧写稳定规则和场景 overlay，user 侧注入 task、root mount、budget、resume、mounted context。
- 适用阶段：把窄路径产品化为可重复的受控自治。

### P3. 质量观测层

- 目标：让 prompt 不只是“能编译”，还要“能被评估”。
- 资产：few-shot 失败模式库、prompt 版本和评测结果绑定、场景回归集。
- 特征：知道哪套 profile / template / example 在什么任务上有效，能定位 prompt 退化。
- 适用阶段：真实试跑复盘、受控自治迭代、多场景扩展前的稳定化。

### P4. 动态策略层

- 目标：让 prompt 随任务、预算、模型和场景动态变化，而不是一套模板打天下。
- 资产：prompt selection rules、模型档位与场景模板联动、显式 / 隐式 Sub-Agent 的调用策略。
- 特征：系统能按任务类型切 prompt profile、seed template、few-shot 组合以及 tool policy overlay。
- 适用阶段：服务器侧独立运行与多场景通用化。

### P5. 自我优化层

- 目标：让 prompt 系统自己进入受控迭代。
- 资产：基于评测的 A/B、回滚、策略版本治理、训练样本反哺。
- 特征：prompt 调整不再靠个人直觉，而是进入持续实验和门禁闭环。
- 适用阶段：评测驱动优化和外部真实用户扩大前。

---

## 5. 阶段总览

先给一个压缩视图，后面再展开每个 gate。

| Gate | 核心目标 | 功能开发重点 | 提示词目标 |
| --- | --- | --- | --- |
| Gate 1 | 证明窄路径能交付 | 专用沙箱、首轮试跑任务、恢复链路、复杂文件拆分验证任务 | P1，开始向 P2 过渡 |
| Gate 2 | 把窄路径产品化为受控自治 | 任务接管协议、显式/隐式 Sub-Agent UX、交付模板、复杂文件拆分正式能力 | P2，补 P3 所需观测 |
| Gate 3 | 服务器侧独立运行 | 工作区编排、后台执行、预算/审计/恢复、文件系统和网络能力边界 | P3 到 P4 |
| Gate 4 | 多场景通用化 | 应用模板、功能性 Sub-Agent、网络和资料能力、场景验收器 | P4 |
| Gate 5 | 评测驱动自我优化 | prompt A/B、模块/策略 A/B、训练样本沉淀、回滚门禁 | P5 |
| Gate 6 | 外部真实用户与发布决策 | 外部用户运行手册、反馈闭环、事故处理、go/no-go 机制 | 稳定运行在 P5 |

### 5.1 当前优先级补充（2026-05-16）

在 Gate 4 正式基线闭环后，当前项目的第一优先级不再是继续扩场景或清理非阻塞技术债，而是补齐“伪无限上下文窗口 / Gate 4 长任务完美实现”。

当前应优先完成的不是更多应用数量，而是下面 4 件事：

1. 冻结 restart protocol、carry-forward package 和 work tree continuity 的正式边界。
2. 把 execution loop 从“单次 run 优先”升级为正式的窗口重启控制器。
3. 建立“手动限制有效窗口 + 100 次上下文窗口重启/压缩 + 更长窗口 reference 对照”的官方评测路径。
4. 以“短窗口效果与长窗口效果相同”为最终目标，补齐质量基线与 provider 级证据。

## 6. 可执行路线

下面的路线不是按自然时间排序，而是按依赖关系排序。只有前一 gate 通过，后一 gate 才值得投入。

### Gate 1. 证明“用户给目标，系统能在窄路径里交付”

这是当前阶段，核心不是“更强”，而是“先成立”。

**做什么**

- 用专用沙箱完成 2 到 3 次内部试跑，优先跑 `YGG-CI-01`、`YGG-CG-01`、`YGG-CG-03`。
- 把“大文件 / 复杂文件拆分”补成正式验证任务，作为编码场景中的高价值子路径。
- 补齐 Windows / MinIO / live provider 的试跑前提说明，消除环境误配噪音。
- 把“只在需求和权限上提问”的交互约束写成明确规则，而不是留在口头原则里。

**大概要开发哪些功能**

- 专用试跑沙箱、隔离工作区、隔离状态根、激活脚本和材料副本。
- 首轮内部试跑所需的任务卡、评分表、工件归档和录屏规范。
- safe-stop / resume 的稳定恢复链路，至少覆盖编码窄路径。
- 大文件 / 复杂文件拆分的最小验证支撑：任务卡、验收项、必要工具和回归点。
- 最少澄清规则的第一版实现，限制系统把技术细节重新推给用户。

**提示词需要达到什么水平**

- 目标等级：`P1`，并开始铺 `P2` 的字段边界。
- 要求：至少有一套 generic PromptProfile 和 coding / research / generic 的基础 SeedTemplate。
- 要求：把“绝不交付半成品”“先调查再判断”“只在需求和权限上追问”明确写进 behaviorGuidelines / outputContract，而不是散落在 note 里。
- 要求：先把显式 Sub-Agent、隐式 Sub-Agent 的边界写成 toolPolicy，哪怕还不是最终版。
- 暂时不要追求动态选模板，也不要急着补大量 few-shot，只要能稳定撑住首轮试跑。

**测试什么**

- 专用沙箱零泄漏：工作区写入、状态写入、MCP 工作区都不得回写真实仓库。
- 首次有效输出时间、总完成时间、人工接管次数、恢复成功率。
- safe-stop / resume 任务的连续性，尤其是恢复后是否知道做到哪一步。
- 大文件拆分任务是否能保持结构、测试与文档同步，不因上下文过长而失控。

**研究什么**

- 显式 Sub-Agent 和隐式 Sub-Agent 什么时候该露出给用户。
- 最少澄清协议：哪些问题必须问，哪些技术细节默认由系统决定。
- 大文件 / 复杂文件拆分应该由规划器做、工具做，还是由场景模块做。
- prompt 资产里哪些是稳定规则，哪些必须继续保留在运行时协议里。

**出口标准**

- 内部试跑全部使用专用沙箱完成，零回写真实仓库。
- 首轮试跑有完整评分表、录屏、trace、工件，不再出现“只记结论，不留证据”。
- 恢复类任务成功率达到 `>= 90%`。
- 前 5 个阻塞项被明确归因到“配置 / 速度 / 体验 / 能力”。

### Gate 2. 把窄路径闭环产品化为“受控自治”

Gate 1 证明的是“能做成”，Gate 2 证明的是“能稳定复现”。

**做什么**

- 固化任务接管协议：目标解析、约束抽取、计划生成、执行、验证、交付。
- 把“工作树协议”纳入任务接管协议的下一版，先固化任务分解、优先图、熵增检查和阶段性重启判定。
- 把“大文件 / 复杂文件拆分”做成正式能力，不依赖临场发挥。
- 明确 Sub-Agent 可见性策略，默认隐藏实现细节，只在授权、风险升级或结果合并时露出。
- 为交付阶段补“自检 + 结果说明 + 未完成项说明”模板，降低半成品交付概率。

**大概要开发哪些功能**

- 任务接管协议：目标解析、约束抽取、计划生成、执行、验证、交付。
- 工作树对象与分解优先图的正式数据结构，作为任务接管、恢复链路和上下文修剪的共享输入。
- 显式 / 隐式 Sub-Agent 的 UX 规则和运行时接线。
- 大文件 / 复杂文件拆分的正式执行能力，而不是仅在试跑里人工引导。
- 交付模板、自检模板、失败说明模板和接管边界模板。
- 首次有效输出、计划质量、返工率等指标的正式采集。

**提示词需要达到什么水平**

- 目标等级：稳定到 `P2`，并补齐 `P3` 所需的观测与样本。
- 要求：PromptProfile / SeedTemplate 字段齐全，system 侧和 user 侧拼接边界稳定。
- 要求：至少为 coding 窄路径补一组高价值 few-shot，覆盖成功例、失败例和恢复例。
- 要求：Prompt 需要能识别 planning / executing / recovering / restarting 这类工作树阶段，而不是只表达统一语气。
- 要求：显式 / 隐式 Sub-Agent 的可见性、工具策略、证据策略要进入结构化字段，而不是依赖零散提示语。
- 要求：outputContract 需要开始区分“结果、证据、待确认项、未完成项”。

**测试什么**

- 同一任务在不同模型档位、不同 auditLevel 下的稳定性差异。
- 编码窄路径在 3 次以上重复执行中的完成率和返工率。
- 工作树驱动的计划、恢复和上下文修剪在重复执行后是否保持一致。
- 复杂文件拆分后再合并时的语义一致性、测试通过率和文档一致性。
- 任务从模糊目标进入正式计划的耗时和提问次数。

**研究什么**

- 用户真正需要看到的中间信息是什么，哪些细节应该隐藏。
- 工作树应该分别落在任务接管协议、运行时数据规格和 Prompt 元数据的哪一层。
- 系统应该如何把“计划质量”与“最终结果质量”分离评分。
- 哪些任务失败来自推理失误，哪些失败来自工具或环境不足。
- few-shot 应该补哪些失败模式，才能真正支撑受控自治而不是只改文风。

**出口标准**

- 同一批窄路径任务重复执行时，验收通过率稳定，人工接管中位数下降。
- 用户澄清回合显著减少，技术选型不再依赖用户驱动。
- “大文件 / 复杂文件拆分”进入固定回归集，而不是临时任务。

### Gate 3. 完成服务器侧独立运行能力

这一步是最终目标里的“服务器端、拥有自己的资源”的真正落地。

**做什么**

- 把当前本地专用沙箱升级为正式运行时工作区编排：创建、挂载、销毁、归档、恢复。
- 明确 Linux 文件系统语义支持范围：复制、移动、链接、权限边界、临时目录、缓存目录。
- 完成长任务后台执行、断点恢复、预算控制、观测、审计、失败归档。
- 将“超图推理协议”从 research draft 提升为 relation reasoning 正式协议，并与 relation-discovery、memory-domain spec 一起收口。
- 建立资源配额与超时策略，防止长任务吞掉服务器资源。

**大概要开发哪些功能**

- 正式工作区编排：创建、挂载、快照、归档、恢复、销毁。
- 长任务后台执行和任务调度；不再依赖当前对话同步盯着跑。
- 网络与文件系统能力边界，包括复制、移动、链接、缓存、临时目录等。
- 资源预算、secret hygiene、失败工件归档和恢复入口。
- 关系平铺、关系原因和模式识别的正式查询面与推理工件，而不是继续把复杂关系推理塞回 Edge.reason 文本。
- 功能性 Sub-Agent 的第一批实现，例如文档导入、上下文清理、资料预读等。

**提示词需要达到什么水平**

- 目标等级：从 `P3` 进入 `P4`。
- 要求：Prompt 已经能根据任务类型、预算、模型档位、是否后台执行来切 profile / template / tool policy。
- 要求：kernelTruth 要准确表述服务器侧事实，例如后台执行、隔离资源、safe-stop / resume、上下文清理；不能继续靠模糊文案兜底。
- 要求：功能性 Sub-Agent 更多通过隐式策略驱动，主 Agent 知道效果边界，但不被内部实现噪音干扰。
- 要求：prompt 必须明确何时保守失败、何时申请权限、何时终止，而不是一味尝试。

**测试什么**

- 工作区隔离、状态根隔离、网络权限和 secret hygiene。
- crash / restart / safe-stop / resume 下的任务一致性。
- 长时间运行任务的资源使用、工件归档完整性和恢复速度。
- 多任务并发下的调度、公平性和资源抢占行为。

**研究什么**

- 哪种沙箱编排方式最适合长期任务：轻量工作区复制、容器、VM 或混合。
- 网络权限默认策略：默认禁用、按任务申请、按应用模板授权。
- 服务器侧成本模型：哪些任务值得后台长跑，哪些任务必须快速失败。
- 关系原因应作为边属性增强、独立推理对象，还是单独的 relation reasoning artifact。
- prompt 的动态选择到底该由规则驱动、场景模板驱动，还是部分交给模型自决。

**出口标准**

- 主要长任务可以脱离当前对话独立运行。
- 恢复与归档成为标准路径，而不是调试能力。
- 服务器侧隔离和审计通过专项安全检查。

### Gate 4. 扩展到多场景通用 Agent

这一步才轮到“通用世界树 Agent”，但前提是前 3 个 gate 已成立。

**做什么**

- 选择 3 个高价值场景做通用化验证：编码、深度研究、长篇创作或 TRPG。
- 把应用插件从“能切应用”推进到“能切默认工作方式、默认工具和默认检索策略”。
- 补齐网络能力、资料抓取、资产导入导出和场景特有的验收器。
- 让功能性 Sub-Agent 成为稳定积木，而不是只用于 PR 协作。

**大概要开发哪些功能**

- 编码、研究、写作 / TRPG 至少 3 个场景的应用模板和验收器。
- 网络检索、资料抓取、资产导入导出和跨场景共享能力。
- 功能性 Sub-Agent 积木化，例如资料导入、批量阅读、上下文清理、结构重组。
- 场景切换时的默认检索、默认工具、默认输出风格装配。

**提示词需要达到什么水平**

- 目标等级：稳定在 `P4`。
- 要求：每个高价值场景都有自己的 SeedTemplate、toolPolicyOverlay、retrievalHints、outputStyle。
- 要求：prompt 不只描述“我是谁”，还要稳定描述“我处于哪种应用”“当前默认工作方式是什么”。
- 要求：显式 Sub-Agent 主要服务协作和风险可视化；隐式 Sub-Agent 主要服务体验和能力增强，这个边界要在场景模板中稳定下来。
- 要求：few-shot 要按场景分层，而不是继续只保留通用示例。

**测试什么**

- 每个场景至少一组快任务、一组跨会话任务、一组恢复类任务。
- 不同场景之间的共享基础能力是否稳定，例如记忆检索、恢复、审计、预算。
- 场景切换时是否会把上一场景的默认行为错误带入当前任务。

**研究什么**

- 哪些能力应该留在内核，哪些继续做模块，哪些应该由应用模板决定。
- 不同场景对“少澄清”和“透明度”的不同要求。
- 通用 Agent 和场景 Agent 的边界：什么时候该落到专用应用。
- 不同场景是否需要不同的 evidencePolicy 和交付风格，而不是共享一套 contract。

**出口标准**

- 至少 3 个场景族有稳定回归集和通过门槛。
- 场景差异主要体现在模板、工具和评分卡，而不是靠硬编码分叉逻辑。
- 用户能在不同场景里保持相似的“只给目标，系统接管”体验。

### Gate 5. 进入评测驱动的自我优化

只有在前面基础稳定后，自我进化才是资产，而不是风险源。

**做什么**

- 把试跑失败、恢复失败、人工接管点沉淀为正式评测数据。
- 用 PromptCompiler、SeedTemplate、模块策略和工具策略做系统级 A/B。
- 通过 training-lab 收集训练样本，但只在评测证明有效后推进微调或蒸馏。
- 让系统能发现“项目自身缺陷”并提出改进，但改动必须走回归门禁。

**大概要开发哪些功能**

- Prompt / 模块 / 工具 / 模型策略的 A/B 和版本治理。
- 试跑失败、恢复失败、人工接管点到评测集的自动沉淀。
- 回滚门禁、收益报告和策略对比视图。
- training-lab 与 prompt / evaluation 的闭环，而不是孤立存在。

**提示词需要达到什么水平**

- 目标等级：进入 `P5`。
- 要求：prompt 调整有版本、观测、评测对照和回滚策略。
- 要求：few-shot、profile、template、tool policy 的迭代能被明确归因，不再出现“换了很多东西，不知道哪个有效”。
- 要求：当系统提出自我改进建议时，prompt 必须约束它给出证据、影响范围和验证计划，而不是只给口号。
- 要求：如果训练或蒸馏不能稳定优于 prompt / tool / runtime 改动，路线应明确继续优先后者。

**测试什么**

- 新策略对既有回归集是否造成倒退。
- 优化后的完成率、首次有效输出时间、恢复成功率是否实质提升。
- 训练或蒸馏是否真的优于记忆 / 工具 / Prompt 改动。

**研究什么**

- 哪类失败适合通过模型训练解决，哪类失败更适合通过运行时或工具解决。
- 自动生成训练数据的噪音控制和版本治理。
- 记忆树检索与模型权重学习之间的最优边界。
- 提示词自我优化和模型训练之间的分工边界，避免两条路线互相污染。

**出口标准**

- 任何“更聪明”的改动都能用评测和试跑数据证明收益。
- 自我优化不再依赖单次灵感，而是进入持续门禁流程。

### Gate 6. 外部真实用户与发布决策

最后一步不是“上线”，而是“是否值得扩大”。

**做什么**

- 扩大到外部真实用户，但仍使用固定材料、固定权限、固定评分。
- 建立 go / no-go 审核机制，决定是否继续扩大范围。
- 补齐面向外部用户的运行手册、问题上报、回滚和事故处理流程。

**大概要开发哪些功能**

- 外部用户版本的运行手册、权限说明、事故处理和反馈入口。
- 面向外部用户的任务模板、评分回收和版本固定机制。
- 发布前质量看板：完成率、首次有效输出、恢复成功率、人工接管率、环境问题比例。

**提示词需要达到什么水平**

- 目标等级：稳定运行在 `P5`。
- 要求：prompt 系统已经足够稳定，不再频繁改主规则；对外阶段更多是微调和版本冻结。
- 要求：不同用户层级看到的解释粒度要稳定，既不能把系统内部噪音全暴露，也不能把失败原因完全隐藏。
- 要求：prompt 必须能稳定维护信任边界，尤其是在失败、权限不足、信息不足时明确说明而不是硬做。

**测试什么**

- 外部用户的完成率、复用意愿、环境问题比例。
- 真实网络、真实仓库、真实资料规模下的稳定性。
- 用户是否仍然需要大量提示词工程，还是已经能只说目标。

**研究什么**

- 用户对“自治”和“可控”的心理边界。
- 哪些失败会直接破坏信任，必须在扩大前彻底解决。
- 成本、速度、透明度之间的可接受平衡点。

**出口标准**

- 对外可以明确说明在哪些场景里比竞品更强，且满足已有真实用户验证门槛。
- 可以稳定回答“为什么值得扩大范围”，而不是靠演示印象做决定。

## 7. 三条并行主线

除了 gate，项目还要沿 3 条长期主线并行推进。

### 主线 A. 产品与交互

- 目标接管协议
- 最少澄清协议
- 显式 / 隐式 Sub-Agent UX
- 交付说明和失败说明规范

### 主线 B. 运行时与平台

- 隔离沙箱与工作区编排
- safe-stop / resume / 长任务后台执行
- 预算、观测、审计、工件归档
- 网络与文件系统能力边界

### 主线 C. 评测与自我优化

- 内部试跑与外部真实用户验证
- 回归集、基线、A/B 与 go / no-go
- Prompt / 模块 / 模型策略的版本治理
- 训练数据与蒸馏是否真的带来收益

## 7.5 新协议纳入策略

- 工作树协议优先服务 Gate 2：先作为 Task Takeover 和运行时数据规格的结构化升级方向，聚焦任务分解、优先图、阶段性重启和熵增控制。
- 超图推理协议延后到 Gate 3：先保留为 research draft，等 relation-discovery、memory-domain spec 和复杂关系推理评测一起成熟后再转正。
- 当前阶段的直接目标不是“把两个协议都立刻变成正式 runtime 硬约束”，而是让它们分别落到最匹配的 gate，避免在 Gate 2 扩边界。

## 9. P1 到 P5 的最小交付物

为了让“提示词需要达到什么水平”不是空话，每一级至少要有下面这些交付物：

### P1 最小交付物

- 1 个 generic PromptProfile。
- 3 个基础 SeedTemplate：coding、research、generic。
- 一份行为准则提炼稿，明确“绝不交付半成品、先调查再判断、只在需求和权限上追问”。

### P2 最小交付物

- 完整 PromptProfile / SeedTemplate 字段映射表。
- PromptCompiler 的稳定拼接规则。
- coding 场景的第一组 few-shot，至少覆盖成功、失败、恢复三类。

### P3 最小交付物

- prompt 版本到评测结果的追踪链。
- 场景回归集中的 prompt 专项观察项。
- 首次有效输出、恢复成功率、返工率的 prompt 相关对照数据。

### P4 最小交付物

- prompt selection rules。
- 按场景和预算切换的 profile / template / tool policy 组合。
- 显式 / 隐式 Sub-Agent 的场景化策略模板。

### P5 最小交付物

- prompt A/B 与回滚流程。
- 收益归因报告模板。
- prompt / 模块 / 训练策略的统一版本治理方式。

## 10. 明确延后事项

为了让路线可行，下面几类事应该延后：

1. 在 Gate 1 没过之前，不继续扩新的大模块或新场景。
2. 在 Gate 2 没过之前，不把“通用世界树 Agent”当作已达成能力对外表述。
3. 在 Gate 3 没过之前，不把“服务器侧独立运行”当作已完成，只能说正在收口。
4. 在 Gate 4 没过之前，不启动大规模外部场景泛化。
5. 在 Gate 5 没过之前，不把训练或微调当作主要提效路径。
6. 在 Gate 2 没过之前，不把超图推理协议提升为正式运行时协议或 memory-domain 硬约束。

## 11. 为什么我认为这条路线可行

这条路线可行，不是因为它宏大，而是因为它收缩了范围：

1. 它直接接在当前仓库的真实用户验证执行阶段之后，没有另起炉灶。
2. 它把最终目标拆成一系列可以被测试、被否证、被暂停的 gate。
3. 它优先解决当前最硬的约束：结果交付、隔离运行、恢复稳定，而不是继续扩模块数量。
4. 它把“大文件 / 复杂文件拆分”“显式 / 隐式 Sub-Agent”“服务器侧资源”这些 note 里的关键问题都挂到了明确阶段上。
5. 它允许持续优化，但每次优化都有门禁，不会把项目重新带回“想到什么就补什么”。

所以，这条路线不是最终版，但已经足够作为接下来一段时间的正式工作主线。
