## 1. 定位

工作树是“我要干什么”根分支的结构化展开，用来表达任务目标、约束、分解、优先级、上下文依赖和恢复状态。

这份文档当前不是正式运行时协议，也不是 Prompt 草稿替代品。它的作用是为 Gate 2 到 Gate 3 的任务接管、阶段性重启和上下文修剪提供一套统一语言，避免这些概念继续散落在 Prompt、TODO 和人工经验里。

## 2. 核心对象

工作树至少要表达以下几类信息：

- 根目标：任务最终要交付什么。
- 约束集合：范围、预算、环境、权限、交付格式和运行边界。
- 分解节点：从粗到细的子任务与子目标。
- 优先图：哪些步骤必须先做，哪些可以并行，哪些依赖上一步的产物。
- 上下文依赖：哪些文件、节点、证据和中间结论是下一步必须保留的。
- 恢复锚点：pause、restart、checkpoint 对应的恢复入口。
- 熵增预算：当前上下文还能承受多少探索、返工和展开。

## 3. 运行语义

工作树对应的最小运行阶段应是：

1. planning：把目标和约束整理成正式计划结构。
2. executing：按优先图推进，并持续更新已完成、阻塞和待验证状态。
3. recovering：在 safe-stop / resume 之后恢复“做到哪里、下一步做什么”。
4. restarting：在上下文过载或长链路返工时做阶段性重启，而不是盲目续写。

这意味着工作树不是单纯的任务清单。它同时是计划对象、恢复对象和上下文修剪对象。

## 4. 解决的问题

工作树主要解决 4 类问题：

- 边界管理：把“该做什么”和“不该做什么”固定下来，减少局部最优漂移。
- 熵增控制：当上下文、返工或探索发散时，给系统一个明确的压缩和重启依据。
- 接管稳定性：把目标解析、约束抽取、计划生成、执行、验证、交付串成同一条结构化链路。
- 恢复一致性：让 safe-stop / resume 恢复的不是一句口头总结，而是带依赖关系的执行状态。

## 5. 当前纳入边界

在当前工程阶段，工作树协议应先服务 Gate 2，而不是一次性扩大成全系统的统一建模：

- 现在就应该做：把工作树作为 Task Takeover 下一版和运行时数据规格扩展的设计依据。
- 现在就应该做：明确任务分解、优先图、阶段性重启和熵增检查的正式字段与工件位置。
- 暂时不要做：把所有记忆节点和关系都改写成工作树结构。
- 暂时不要做：在 Gate 2 重复执行证据还不足时，把工作树变成所有任务的强制硬约束。

## 6. 升级条件

工作树从 research draft 升级为正式协议，至少要满足以下条件：

1. Task Takeover 协议已证明可以稳定生成 objective / constraints / plan / verification / delivery。
2. 运行时数据规格已能正式表达任务分解、优先关系和恢复锚点。
3. safe-stop / resume 与上下文修剪链路能消费这些对象，而不是只消费自然语言摘要。
4. 复杂文件拆分和重复执行样本能证明工作树确实减少返工，而不是只增加文档层复杂度。
