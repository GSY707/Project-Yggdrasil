# 基座面向用户界面：客服型 Agent 与产品正门

日期：2026-06-05

## 1. 设计目标

基座面向用户的界面要从“控制台首页”变成“用户正门”。用户第一次进入时，不应该先看一堆系统模块，而应该看到：

1. 我现在能做什么。
2. 系统是否准备好。
3. 我该选择哪个应用。
4. 我可以直接问谁。
5. 我的请求如何变成一个可启动任务。

这个正门的核心是客服型 Agent。它不是普通闲聊机器人，而是项目内置的产品向导、应用路由器、简单支持台和任务 Prompt 代写助手。

## 2. 客服型 Agent 的定位

### 2.1 它应该懂什么

客服型 Agent 必须非常了解本项目的当前能力和边界：

- 当前可用：本地产品模式、Web 首次任务路径、应用模板、文本素材导入、任务启动、任务详情、LLM 工作分析、本地备份/恢复命令。
- 当前计划中：完整 Docker Compose 产品栈、桌面安装包、Web 删除/清理、托管 / SaaS、官方远端数据托管、远端备份、远端删除。
- 当前高级入口：Prompt、MCP、评测、观测、协作、训练、原始 JSON、CLI。
- 当前数据边界：本地 state root、provider key、LLM provider 出机、Langfuse / OTel 出机、本地备份位置。

它不能把计划中能力说成已经支持，也不能用“以后会有”掩盖当前阻塞。

### 2.2 它应该做什么

| 用户意图 | Agent 应做的事 |
| --- | --- |
| “这个项目是做什么的” | 用普通语言解释产品，不讲内部里程碑名 |
| “我想完成某件事” | 追问必要约束，推荐应用包和任务模板 |
| “帮我写 Prompt” | 把松散想法转成任务标题、目标、验收标准、素材需求、预算和模型建议 |
| “现在能不能开始” | 检查 Core API、worker、provider key、state root、工作区和数据边界 |
| “哪个应用适合我” | 用场景语言推荐，而不是暴露 appId |
| “为什么失败” | 用错误原因和下一步修复动作解释，不只显示异常字符串 |
| “数据在哪里” | 指向本地数据、日志、备份、provider 和远端计划的真实边界 |
| “我要高级调试” | 路由到 Prompt、MCP、评测、观测、日志或任务分析页 |

### 2.3 它不应该做什么

- 不要把客服 Agent 设计成营销聊天气泡。
- 不要让它伪造任务进度。
- 不要绕过用户确认直接启动高成本任务。
- 不要把 `.env`、raw JSON、appId、branchId、spaceId 作为普通用户默认输入。
- 不要让它替代应用包界面。它负责路由和解释，具体场景体验仍由应用包承载。

## 3. 首页信息架构建议

建议把基座首页拆成 5 个区域：

1. 启动状态：是否可创建第一个任务，缺什么，怎么修。
2. 客服型 Agent：问问题、说目标、代写任务 Prompt、推荐应用。
3. 快速开始：导入素材、选择应用、创建任务。
4. 最近工作：最近任务、运行中任务、待处理失败、等待批准。
5. 高级入口：折叠到高级模式，不压住普通主线。

普通导航建议：

| 一级入口 | 面向用户的含义 |
| --- | --- |
| 开始 | 首页、客服 Agent、首次启动检查、最近工作 |
| 任务 | 当前工作、结果、继续/暂停/恢复 |
| 应用 | 按目标选择应用包 |
| 素材 | 导入、管理和附加材料 |
| 数据与安全 | 数据位置、备份、恢复、隐私边界 |
| 高级 | Prompt、MCP、评测、观测、协作、训练、调试 |

现有侧边栏里 `节点`、`协作`、`训练`、`MCP`、`Prompt`、`评测`、`观测` 等入口不应在普通模式与任务主线同权重展示。

## 4. 客服型 Agent 的交互状态

### 4.1 标准流程

```text
用户输入目标
-> Agent 识别意图
-> Agent 追问缺失信息
-> Agent 推荐应用与模板
-> Agent 生成任务草案
-> 用户确认或修改
-> 创建草稿
-> 用户选择启动或稍后启动
```

任务草案至少包含：

- 标题
- 目标
- 推荐应用
- 推荐模板
- 输入素材需求
- 预期产物
- 成本或 token 预算建议
- provider / model 建议
- 需要用户确认的风险

### 4.2 应用路由

客服 Agent 推荐应用时，应按用户目标说人话：

| 用户说法 | 推荐方向 |
| --- | --- |
| “帮我查清楚一个问题” | Deep Research |
| “我要系统学习一个领域” | Graduate Researcher |
| “我要从零做一个软件” | Coding Greenfield |
| “我有一堆资料要整理成知识库或文章” | Knowledge Studio |
| “我要维护旧项目” | Coding Inherit |
| “我要写长篇故事或世界观” | Epic Writing |

推荐结果需要解释“为什么选它”和“它通常产出什么”，而不是只给名称。

### 4.3 Prompt 代写

Prompt 代写不是暴露 prompt profile 编辑器，而是把用户的自然请求转成任务输入。界面应支持：

- 目标澄清
- 输出格式选择
- 约束填写
- 资料附加
- 预算级别
- 工具权限级别
- 启动前预览

启动前必须有确认页或确认区。确认区应告诉用户：

- 将使用哪个应用。
- 将发送哪些素材摘要或上下文给 provider。
- 预算上限是什么。
- 任务完成后在哪里看结果。

## 5. 错误与支持体验

客服 Agent 应接入启动检查和错误解释：

| 错误类型 | 用户看到的解释 |
| --- | --- |
| Core API 不可访问 | 本地产品服务没有启动或端口不可用，提供 `corepack pnpm yggdrasil:up` 作为修复路径 |
| provider key 缺失 | 需要配置至少一个模型供应商 key，并说明 key 不应写入仓库 |
| worker / queue 不可用 | 后台执行器未运行，任务可能停在 queued |
| 数据库不可用 | 本地依赖未启动或迁移未执行 |
| 应用未装配 | 应用包缺 manifest、dashboard、prompt 或配置引用 |
| 预算不足 | 解释 token/cost 预算和追加后续跑入口 |
| 任务等待批准 | 解释 `awaiting-approval`，提供批准完成或请求修订 |

设计要求：错误提示必须给下一步，不要只显示堆栈、HTTP 状态或英文异常。

## 6. 外包团队交付要求

这一组界面需要交付：

1. 首页 IA 和导航重构。
2. 客服型 Agent 面板的完整状态图。
3. 用户问答、应用推荐、Prompt 代写、任务确认、错误修复五条关键流程。
4. 普通模式 / 高级模式切换策略。
5. 文案体系：项目解释、能力状态、错误提示、确认提示、隐私提示。
6. 与现有实现的映射：`overview-page.tsx`、`task-launch-panel.tsx`、`applications-page.tsx`、`release-page.tsx`。

## 7. 验收问题

验收时要求新用户能回答：

- 我现在能做哪几类事？
- 我应该从哪个应用开始？
- 我的想法如何变成任务？
- 启动前我是否知道成本、素材、provider 和结果位置？
- 系统如果没准备好，我知道该修什么吗？
- 高级工具在哪里，但它们是否没有干扰第一次成功？
