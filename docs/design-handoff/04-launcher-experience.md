# 启动器设计需求文档

日期：2026-06-07

## 1. 设计目标

启动器是世界树计划从“源码项目”走向“普通用户可安装产品”的第一层界面。它的目标不是把命令行包一层壳，而是让用户安装后能完成：

1. 理解这是什么产品、当前安装了哪个应用包。
2. 完成必要配置，尤其是 Docker Desktop、端口、provider key、本地数据位置。
3. 启动本地产品栈并打开正确的应用界面。
4. 看懂当前运行状态、错误原因和下一步动作。
5. 进入备份、恢复、更新、日志和卸载等维护动作。

设计团队要把启动器当作“本地产品入口 + 应用包发行入口 + 故障支持入口”来设计。普通用户不应该看见 `uv sync`、`corepack pnpm product:up`、Compose 服务名、raw `.env` 或内部 appId，除非进入高级模式。

## 2. 当前真实基础

当前仓库已有可参考实现，但不是正式签名发行版：

- 产品栈：`infra/docker-compose.product.yml`
- 产品命令：`corepack pnpm product:*`
- 本地产品一键启动：`corepack pnpm yggdrasil:up`
- Windows 桌面封装预览：`packaging/desktop/windows/`
- 桌面控制脚本：`packaging/desktop/windows/Yggdrasil.Desktop.ps1`
- 安装脚本：`packaging/desktop/windows/Yggdrasil.Install.ps1`
- 托盘脚本：`packaging/desktop/windows/Yggdrasil.Tray.ps1`
- 应用包目录：`applications/*/yggdrasil.app.yaml`
- 应用详情入口：`/applications/{appId}`
- 应用任务入口：`/tasks?appId={appId}`

当前缺口：

1. 桌面安装包仍未签名。
2. 现有 ZIP 只打包桌面脚本，不打包完整项目和指定应用包。
3. 安装器没有应用包选择、应用包校验、默认激活和应用专属快捷方式。
4. 启动入口只打开 Web 根页面，没有深链接到某个应用包。
5. Docker、provider key、端口冲突、服务启动失败等错误仍偏工程化。

设计文档应基于这些真实边界，不要把尚未实现的自动签名、静默更新、云同步或官方托管画成当前能力。

## 3. 用户与使用场景

### 3.1 普通本地用户

用户只想打开一个能完成具体任务的应用，比如 Deep Research Lab、Learning Coach 或某个外部团队交付的应用包。

他们关心：

- 是否安装成功。
- 是否需要启动 Docker Desktop。
- 模型 key 是否配置好。
- 点击哪个按钮开始使用。
- 数据在本机哪里。
- 出错时该怎么处理。

他们不关心：

- Compose 服务拓扑。
- Python / Node 依赖。
- migration、NATS、Temporal、OTel 等内部系统。
- raw manifest 或 appId。

### 3.2 应用包购买者 / 试用者

用户安装的不是抽象的“世界树计划”，而是“某个应用包 + 世界树基座”的组合。

他们需要：

- 桌面快捷方式直接叫应用包名称，例如 “Deep Research Lab”。
- 启动后直接进入该应用详情页或任务启动页。
- 明确知道这是本地运行，哪些数据会出机给模型 provider。
- 在应用不可用时看到应用包校验错误，而不是泛化的系统失败。

### 3.3 高级用户 / 维护者

维护者需要能看到更多控制项：

- 产品栈状态。
- 日志。
- 备份、恢复、快照、升级、回滚。
- 端口与环境变量。
- Docker Desktop 状态。
- 手动更新检查。

这些能力应进入高级/维护模式，不应挤占普通用户首屏。

## 4. 产品定位

启动器的产品定位：

> 像一个本地应用的控制中心，而不是开发者终端。

它应该提供三个层级：

1. 普通模式：打开应用、启动/停止、健康检查、必要设置。
2. 支持模式：错误诊断、日志导出、备份恢复、更新。
3. 高级模式：端口、环境变量、Compose 服务、原始日志、命令等技术细节。

默认首屏必须是普通模式。高级模式要可达，但不能成为默认路径。

## 5. 信息架构

### 5.1 主窗口

主窗口建议包含：

1. 顶部身份区：产品/应用包名称、版本、安装状态。
2. 状态总览：本地服务、Docker、provider key、数据位置、最近备份。
3. 主动作：打开应用、启动、停止、重启。
4. 应用入口：当前内置应用包、直达应用页、直达新任务页。
5. 支持入口：诊断、日志、备份恢复、更新。
6. 高级入口：端口、环境变量、服务详情。

### 5.2 托盘菜单

托盘菜单建议包含：

1. 打开当前应用。
2. 打开工作台。
3. 启动 / 停止 / 重启。
4. 状态。
5. 诊断。
6. 备份。
7. 恢复最近备份。
8. 更新检查。
9. 打开日志。
10. 退出托盘。

托盘菜单文案必须是用户语言，不应出现 `product:up`、`docker compose` 这类命令名。

### 5.3 安装向导

安装向导建议拆成：

1. 欢迎与应用包说明。
2. 安装位置与数据位置。
3. Docker Desktop 检查。
4. Provider key 配置。
5. 应用包校验。
6. 快捷方式选择。
7. 安装完成与首次启动。

## 6. 核心流程

### 6.1 首次安装

流程：

1. 用户打开安装器。
2. 安装器展示产品名称、内置应用包、版本和本地运行说明。
3. 用户选择安装位置、数据位置和是否创建桌面/开始菜单快捷方式。
4. 系统检查 Docker Desktop。
5. 用户配置 provider key，或选择稍后配置。
6. 系统校验应用包 manifest、dashboard、prompt、memory 和默认配置。
7. 安装完成后展示“打开应用”和“稍后打开”。
8. 如果用户选择打开应用，启动器启动产品栈并进入应用包页面。

设计要求：

- 用户可以明确知道“安装成功但尚未配置 provider key”和“安装失败”的区别。
- 如果缺 provider key，可以允许安装完成，但不能表达成已经可启动真实任务。
- 如果 Docker 未安装或未启动，要给出清晰动作：启动 Docker Desktop、稍后重试、查看帮助。

### 6.2 日常打开应用

流程：

1. 用户点击应用专属桌面快捷方式。
2. 启动器检查产品栈是否已经运行。
3. 如果未运行，显示启动进度。
4. 健康检查通过后打开 `/applications/{appId}` 或 `/tasks?appId={appId}`。
5. 如果启动失败，显示具体错误和推荐动作。

关键体验：

- 快捷方式名称应默认使用应用包 `displayName`，不是 “Yggdrasil Desktop”。
- 首次打开可以进入应用详情页；之后可配置为直接进入任务启动页。
- 用户不应看见后台命令窗口闪烁。

### 6.3 状态诊断

诊断页应按用户可理解顺序展示：

1. Docker Desktop：未安装 / 未启动 / 正常。
2. 产品服务：未启动 / 启动中 / 正常 / 部分失败。
3. Web 工作台：可访问 / 不可访问。
4. Core API：可访问 / 不可访问。
5. Provider key：未配置 / 配置但不可用 / 可用。
6. 端口：可用 / 冲突。
7. 数据位置：可写 / 不可写 / 空间不足。
8. 应用包：未发现 / 校验失败 / 可用。

每个状态必须有：

1. 用户可读标题。
2. 简短解释。
3. 推荐操作。
4. 可复制的技术详情。

技术详情默认折叠。

### 6.4 备份与恢复

普通用户入口：

- 创建备份。
- 查看最近备份。
- 恢复最近备份。
- 恢复指定备份。

必须表达：

- 备份覆盖哪些数据。
- 恢复会停止当前产品栈。
- 恢复前建议自动创建保护性快照。
- 恢复完成后如何重新打开应用。

高级信息：

- Compose volume 名称。
- 备份路径。
- 备份命令和日志。

### 6.5 更新与回滚

当前实现只支持手动检查和手动应用 fast-forward 更新。设计不能画成静默自动更新。

更新界面需要区分：

1. 已是最新。
2. 有可应用更新。
3. 有更新但不是 fast-forward，不能自动应用。
4. 更新失败，可回滚。
5. 更新前备份失败。

更新流程建议：

1. 检查更新。
2. 展示版本差异摘要。
3. 创建保护性备份。
4. 应用更新。
5. 重建产品栈。
6. 运行健康检查。
7. 成功后打开应用；失败时提供回滚。

## 7. 关键界面清单

外包团队至少要产出以下界面：

1. 安装欢迎页。
2. 应用包说明页。
3. 安装位置与数据位置页。
4. Docker 检查页。
5. Provider key 配置页。
6. 应用包校验页。
7. 安装完成页。
8. 启动器主窗口。
9. 启动进度窗口。
10. 启动失败窗口。
11. 托盘菜单。
12. 状态诊断页。
13. 日志页。
14. 备份与恢复页。
15. 更新与回滚页。
16. 高级设置页。
17. 卸载确认页。

每个界面都要覆盖：

- 空状态。
- 正常状态。
- 警告状态。
- 错误状态。
- 长时间等待状态。
- 操作成功后的下一步。

## 8. 文案规则

### 8.1 用户语言

推荐文案：

- “正在启动本地服务”
- “Docker Desktop 还没有启动”
- “模型密钥未配置，暂时只能创建草稿”
- “当前应用包可以使用”
- “打开 Deep Research Lab”
- “创建备份”
- “恢复到这个备份”

避免文案：

- “docker compose up failed”
- “providerStatus=false”
- “core-api unhealthy”
- “YGGDRASIL_PRODUCT_ENV_FILE missing”
- “run product:up”

技术信息可以保留，但必须放在“技术详情”折叠区。

### 8.2 能力边界

必须明确：

- 当前是本地优先产品。
- 模型调用会把必要上下文发送给用户配置的 provider。
- 当前没有官方 SaaS 托管承诺。
- 当前没有静默自动更新。
- 未签名安装包可能触发 Windows 安全提示。
- provider key 不应写进公开模板或快捷方式。

## 9. 视觉与交互方向

启动器应更像安静可靠的本地工具，而不是营销页。

建议方向：

1. 信息密度中等，状态清晰，不做大面积装饰。
2. 主动作突出，但不要用夸张 hero。
3. 错误提示要像支持中心，不像开发日志。
4. 应用包身份要明显：名称、图标、用途、版本、发布方。
5. 技术细节收进高级面板。
6. 使用稳定的状态色：正常、警告、错误、处理中。
7. 适配 Windows 桌面体验：主窗口、托盘、通知、快捷方式、系统安全提示。

不要做：

- 只有一张欢迎图的安装页。
- 把命令输出作为主要界面。
- 把所有服务状态平铺给普通用户。
- 用大段解释文字代替可执行按钮。
- 把产品栈错误包装成无法行动的泛化提示。

## 12. 验收标准

设计方案至少要满足：

1. 用户安装后能判断下一步是“配置 key”“启动 Docker”还是“打开应用”。
2. 用户可以从应用专属快捷方式直接进入该应用，而不是先进入内部控制台。
3. 用户能看懂产品是本地运行，知道数据和 provider 出机边界。
4. 用户能区分安装成功、配置未完成、启动失败、应用包校验失败。
5. 用户能创建备份，并理解恢复的影响。
6. 用户能检查更新，但不会误以为系统会静默自动更新。
7. 高级用户能找到日志、端口、服务状态和技术详情。
8. 普通用户不需要阅读 README 或运行命令。
9. 当前未实现能力不会被画成可用能力。
10. 新设计不沿用旧命令行/控制台作为普通用户主路径。

## 13. 需要下沉或删除的旧表达

这些内容不应出现在普通启动器主线：

1. 多终端手动启动命令。
2. `uv sync`、`corepack pnpm install`。
3. `docker compose` 原始命令。
4. Compose 服务名和容器日志流。
5. raw `.env` 编辑作为普通配置方式。
6. 内部 appId 作为用户主识别信息。
7. 未签名、未完成、计划中的能力被包装成正式发行能力。

这些内容可以保留在高级模式、开发者文档或技术详情中。

## 15. 设计结论

启动器必须是 GUI-first 的产品正门。它应把用户带到“我安装了哪个应用、现在能不能用、下一步点哪里”的清晰状态，而不是把用户推回命令行。

对外发行时，最理想的体验是：

1. 用户安装 “某个应用包 + 世界树基座”。
2. 桌面出现该应用包的快捷方式。
3. 用户点击快捷方式。
4. 启动器检查并启动本地产品栈。
5. 浏览器或桌面 Web 容器直接打开该应用包界面。
6. 用户从模板创建任务并开始使用。

设计团队应围绕这条路径做主方案，再把备份、恢复、更新、诊断和高级配置作为辅助路径。
