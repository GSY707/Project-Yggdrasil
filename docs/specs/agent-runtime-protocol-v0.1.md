## 1. 目标

把以下内容从“设计想法”提升为正式运行协议：

- 建树算法
- 启动流程
- 根节点挂载
- 困难任务的上下文整理
- 第二版任务暂停与无感恢复

## 2. 模块划分原则

模块不是按页面划分，也不是按技术栈随意拆分，而是按三件事划分：

- 是否是全系统共享且必须长期稳定的能力。
- 是否会高频替换或按项目选择性启用。
- 是否本质上只是外部依赖接入。

因此划分结果是：

- Kernel：所有任务都依赖、且一旦出错会影响全系统一致性的能力。
  - 节点、关联、版本、任务、预算、审计、模块注册表、统一配置、核心事件。
- 第一版核心模块：在第一版必须交付，但仍应可单独替换的能力。
  - text-memory
  - context-pruning
  - subagent-pr
- 第二版增强模块：能力明确重要，但允许后置交付。
  - multimodal-memory
  - memory-maintainer
  - relation-discovery
  - memory-governance
  - training-lab
- Adapter：不是业务能力，而是外部系统接入。
  - model-router
  - oidc
  - object-store
  - event-bus
  - media-providers

这个划分的核心原则是：

- 共享状态进 Kernel。
- 业务增强进 Module。
- 第三方接入进 Adapter。

## 3. 提示词与协议的分工

以下内容不能只放在提示词里：

- 建树算法：它是工作流 + 模型决策 + 持久化提交，不只是“提示模型怎么分”。
- 启动流程：它是系统初始化顺序，不只是“开场白”。
- 根节点挂载：它是上下文装配协议，不只是“提示词模板”。
- 困难任务上下文整理：它是受预算约束的修剪流程，不只是“让模型自己总结”。
- 任务暂停：它是持久化和恢复协议，不只是“提醒模型下次继续”。

提示词只负责：

- 行为准则。
- 场景化身份模板。
- 模型在单步推理中的操作偏好。

协议负责：

- 触发条件。
- 输入输出结构。
- 读写顺序。
- 持久化与恢复。
- 审计与事件。

## 4. 建树算法协议

### 4.1 目标

把大量零散资料转化为可检索、可压缩、可持续整理的记忆树结构。

### 4.2 输入

- importJob
- sourceFiles 或 sourceStream
- importPolicy
- tokenBudget
- optional subAgentBudget

### 4.3 输出

- 临时节点集合
- 候选父节点方案
- 候选关联边方案
- 导入过程审计记录

### 4.4 流程

1. 系统接收导入任务，创建 importJob。
2. 如资料规模较大，主 Agent 派出 Sub-Agent 预读，形成有相关性顺序的输入流与全局概览。
3. 系统把原始资料切分为可处理片段，生成 orderedFragments。
4. 建树模块基于片段与全局概览，生成临时节点候选与父节点候选。
5. 关系发现模块或规则引擎给出关联边建议，算法来源可包括 HippoRAG、PPR、关键词共现、向量近邻。
6. 主 Agent 或授权 Sub-Agent 生成结构化建树计划。
7. Kernel 以临时节点方式写入，尚不要求一次性完成最终树形。
8. 后续由整理任务继续做归并、上浮、重排与关联补全。

### 4.6 冻结决策

- 建树算法生成的大规模重排、合并、删减不需要人工审批阈值。
- 但所有结果都必须可回溯、可回滚、可对比。

### 4.5 协议边界

- 提示词可帮助模型更好地产生候选结构。
- 最终落库、版本记录、事件发布、后续整理调度由系统负责。

## 5. 启动流程协议

### 5.1 目标

让 Agent 每次启动时都能以稳定顺序获得系统认知、世界认知与当前任务认知。

### 5.2 流程

1. 系统初始化，不依赖当前会话上下文。
2. 加载 Kernel、Module Host、必要 Adapter 与模块注册表。
3. 解析当前项目、任务、预算、暂停状态、恢复状态。
4. 读取三个根分支的挂载材料。
5. 编译系统提示词与场景种子模板。
6. 组装启动上下文。
7. 如果存在 resumeMessage、pauseSnapshot 或 restartMessage，则按恢复优先级注入。
8. 创建新的 AgentRun 并开始工作。

### 5.3 恢复优先级

- paused task snapshot
- restart message
- unfinished task state
- cold start default context

## 6. 根节点挂载协议

### 6.1 根节点结构

- 我是谁：人格、偏好、工具能力、记忆修改积极度、权限等级、进化指令。
- 我在哪：项目摘要、外部世界摘要、知识边界、来源规则。
- 我要干什么：工作树状态、留言、当前目标、预算、暂停/恢复信息。

### 6.2 挂载规则

- 根节点不是简单全文拼接，而是按预算和优先级组装。
- Kernel 必须强制挂载最小必要字段。
- 模块可以通过 agent.startup.mount-root hook 增加补充挂载片段。
- 模块不得删除 Kernel 强制挂载项。

### 6.4 身份根分支写入规则

- “我是谁”允许长期改写。
- 但 canonical identity 的正式写入只能由 Kernel 或内核态治理流程执行。
- 普通任务、Sub-Agent 和普通模块只能提交 overlay 或 rewrite proposal。

### 6.3 输出格式

启动上下文至少包含：

- rootSummary
- mountedNodeRefs
- taskObjective
- resumeMessage
- budgetState
- activeCapabilities

## 7. 困难任务上下文整理协议

### 7.1 目标

当单纯重启仍不足以解决上下文过载时，保留下一步任务所需信息，压缩或移除弱相关内容。

### 7.2 触发条件

- 预计下一轮上下文会超预算。
- 当前任务在探索阶段持续消耗上下文。
- 用户或策略显式请求修剪。

### 7.3 流程

1. 主 Agent 明确下一步目标。
2. 系统冻结当前上下文快照。
3. context-pruning 模块生成修剪计划，区分 retained、compressed、dropped 三类信息。
4. 辅助 Agent 或模块执行修剪，并生成 rationale。
5. Kernel 校验受保护信息未丢失。
6. 写入 pruning 结果与审计记录。
7. 新的 AgentRun 从修剪后的上下文继续。

### 7.4 保留原则

- 下一步目标的直接依赖信息必须保留。
- 已验证事实优先保留。
- 未完成推理链中断风险高的内容优先保留。
- 可重新从记忆树召回的信息可以被压缩。

### 7.5 冻结决策

- 上下文修剪在任何风险级别都不要求人工确认。
- 修剪的约束来自 protectedRefs、审计、版本和可恢复性，而不是人工审批。

## 8. 第二版任务暂停与无感恢复协议

### 8.1 目标

当用户请求暂停时，系统不再继续触发下一次 LLM 调用，而是在当前安全停止点保存任务，并在下次启动后无感恢复。

### 8.2 语义

- pause 不是强杀当前回答。
- pause 在“下一次安全停止点”生效。
- 安全停止点默认是：当前输出结束、待写入记忆冲刷完成、关键工具调用状态可持久化。

### 8.3 流程

1. 用户或策略发出 pause 请求。
2. 系统写入 task.pause.requested 事件。
3. 当前回答结束后，调用 task.pause.prepare hook。
4. 冲刷异步写入、记录未完成外部动作、生成 TaskSnapshot。
5. 写入 paused 状态与 resumeToken。
6. 停止继续调度下一次 LLM 调用。
7. 下次启动时优先读取 TaskSnapshot 与 resumeMessage。
8. 调用 task.resume.rehydrate hook，恢复工作状态并继续执行。

### 8.4 第一版必须预埋的基础能力

- TaskSnapshot 数据对象。
- task.pause.requested、task.paused、task.resume.requested、task.resumed 事件。
- hook：task.pause.prepare、task.resume.rehydrate。
- 任务状态机支持 paused。
- 待写入记忆冲刷机制。

## 9. 第二版能力对第一版的基础要求

以下第二版能力虽然延后交付，但第一版必须预埋基础字段和边界：

### 9.1 高级权限与共享记忆空间

第一版就必须保留：

- projectId
- spaceId
- branchId
- ownerSubject
- mountMode

否则第二版会大面积改表、改事件、改导入导出协议。

### 9.2 任务暂停

第一版就必须保留：

- TaskSnapshot
- paused task state
- resumeToken
- safe-stop semantics

### 9.3 多项目与导入导出

第一版建议就采用 package 化思路：

- 一个任务或一棵记忆子树可以导出为 package。
- package 至少包含 manifest、nodes、edges、versions、assets、source refs。

### 9.4 共享挂载语义

- 第二版共享空间必须同时支持只读挂载、写时复制、双向同步三种工作状态。
- 因此第一版不得把挂载模式写死成单枚举常量或隐含行为。

## 10. 泛型工具分发与能力注册

### 10.1 目标

把原始设计中的“超级路由”正式化，避免各模块直接向 Agent 暴露不一致的工具接口。

### 10.2 规则

- 对 Agent 暴露的统一入口是泛型工具分发器，而不是模块私有 RPC 集合。
- 每个工具都必须先注册 ToolDescriptor，再允许被分发器发现。
- 工具调用结果必须形成 ToolInvocationRecord。
- 高风险工具必须附带权限声明与审计记录。

### 10.3 模块边界

- 模块负责声明工具能力。
- Kernel 负责统一注册、鉴权、调度、审计与错误归一化。

## 11. 模型能力分析与自动任务分配

### 11.1 目标

把“让合适的模型做合适的事”从策略口号提升为正式运行能力。

### 11.2 规则

- 主 Agent 启动 Sub-Agent 前，或进入新阶段任务前，应允许触发模型路由分析。
- 自动选模必须产出 ModelRouteDecision。
- 路由分析至少考虑质量、成本、延迟、上下文需求四个维度。
- 如果没有满足预算或质量门槛的模型，系统应显式失败，而不是静默猜测。

## 12. 已冻结产品决策

- “我是谁”允许长期改写，但只能内核态改写 canonical identity。
- 建树算法的大规模重排、合并、删减不需要人工审批。
- 困难任务上下文修剪在任何风险级别都不需要人工确认。
- 导入导出 package 的最小正式粒度是项目级。
- 第二版共享空间必须同时支持只读挂载、写时复制、双向同步。

## 13. 当前建议默认值

以下我建议直接作为默认值落地，不必再等：

- 模块宿主与核心 API 分成独立进程，但第一版可以同机部署。
- 模块配置采用数据库为主、文件覆盖为辅的模式。
- 第一版单项目运行，但所有关键对象都必须携带 projectId。
- 第一版不开放第三方前端路由注入。
- pause 默认是手动触发，不做自动暂停策略。

## 14. 仍可继续细化的技术问题

以下问题仍可继续细化，但它们不再阻塞 v0.1 规格冻结：

1. identity overlay 的合并策略是自动合并、延迟合并，还是周期治理合并。ans:自动合并
2. bidirectional 挂载发生冲突时的默认冲突解决策略。ans：如果是主agent+sub-agent，以主agent优先，打回sub-agent的修改，重新写。如果是双sub-agent，先改的生效，打回后改的。
3. package 导出是否需要支持匿名化导出变体。ans：是
4. ModelRouteDecision 的评分权重是全局固定还是任务类型可配。ans：任务类型可配

## 15. 结论

建树算法、启动流程、根节点挂载、困难任务上下文整理、任务暂停都属于运行时协议，不应退化成“写在提示词里的约定”。提示词只是这些协议中的一个输入源，不是协议本身。
