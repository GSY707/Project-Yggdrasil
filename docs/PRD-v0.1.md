## 1. 背景

世界树计划已经通过 MVP 在 TRPG 场景验证了核心思路的可行性：

- 动态加载记忆可以缓解上下文窗口限制。
- 对上下文进行裁剪与压缩可以提升长任务的持续执行能力。
- 针对场景预设“我是谁”“我在哪”的种子上下文，有助于 Agent 更稳定地进入工作状态。

当前问题不再是“这个想法是否成立”，而是“如何把它做成一个长期可运行、可恢复、可评测、可扩展、可插拔的 Agent 系统”。

## 2. 问题定义

现有 LLM 系统在长任务中存在四类核心问题：

1. 上下文窗口有限，无法稳定承载长期任务状态。
2. 普通对话式 Agent 缺少结构化长期记忆，检索结果难以保持精度与可追溯性。
3. 当上下文过长或任务中断时，系统难以稳定恢复思路。
4. 系统能力一旦增长，容易演化成难以维护的巨石架构，无法单独启停和替换功能模块。

世界树计划要解决的是“让 Agent 以结构化记忆和模块化能力为基础，持续完成长时任务”。

## 3. 产品定位

世界树计划不是一个普通聊天应用，也不是单一检索工具。

它的产品定位是：

- 一个面向长任务的 Agent 操作系统。
- 一个以记忆树为核心数据结构的长期记忆基础设施。
- 一个支持可插拔能力模块的智能体平台。

## 4. 产品目标

### 4.1 核心目标

- G1：建立可长期维护的记忆树内核，让 Agent 的有效记忆范围超出当前上下文窗口。
- G2：建立可恢复的任务运行机制，在上下文重启后仍能继续执行任务。
- G3：建立可追踪的检索与写入链路，让记忆、来源、版本、变更原因都可回溯。
- G4：建立可插拔的模块平台，让多模态、训练、权限、整理等能力可以独立交付。
- G5：建立可评测的工程闭环，使系统优化不依赖主观感觉。

### 4.2 第一版成功标准

- 主 Agent 能完成一次完整任务，并在上下文重启后继续执行。
- 记忆检索结果同时返回节点内容、子节点名、关联节点名、来源信息。
- Sub-Agent 能在独立分支工作，并通过 PR 机制提交修改。
- 任意节点都可以查看历史版本与来源。
- 在基准任务上，记忆树方案相对无记忆基线有稳定提升。
- 系统关键链路可追踪，能够定位失败发生在检索、压缩、选模还是写入。

## 5. 非目标

以下内容不属于第一版目标：

- 完整多租户平台。
- 完整 Linux 式权限系统。
- 任意第三方模块的运行时热插拔。
- 训练后的自有模型成为默认主模型。
- 多模态能力作为第一版必须项。

这些能力会在模块化基础稳定后，以独立模块形式推进。

## 6. 目标用户与典型场景

### 6.1 第一阶段目标用户

- 需要长期维护上下文的个人开发者。
- 进行复杂知识整理的研究者与创作者。
- 需要长时间运行、分任务协作的 Agent 系统设计者。

### 6.2 典型场景

- 场景 A：代码开发
  - Agent 需要跨多轮、多文件、多阶段地维护项目状态。
- 场景 B：TRPG 或复杂叙事
  - Agent 需要稳定维护世界观、角色、事件链和当前剧情推进状态。
- 场景 C：科研调研
  - Agent 需要对大量资料建树、关联、压缩、引用与回溯。
- 场景 D：创意写作
  - Agent 需要持续维护角色、风格、伏笔与世界设定。

## 7. 产品范围

### 7.1 第一版必须范围

- 文本记忆树。
- 三个根分支：我是谁、我在哪、我要干什么。
- 节点增删改查、关联边、版本历史、来源标注。
- 混合检索与上下文组装。
- 启动流程、断点恢复、上下文重启。
- 主 Agent / Sub-Agent 分支协作与 PR 机制。
- 模块注册表、模块协议、模块宿主、模块启停。
- Web 控制台基础能力。
- 评测、日志、追踪、预算与审计。

### 7.2 延后范围

- 多模态记忆模块。
- 自动整理与软遗忘模块。
- 主动关联发现模块。
- 高级权限与共享记忆空间模块。
- 训练与蒸馏实验模块。
- 任务暂停与无感恢复能力。

## 8. 功能需求

### FR-001 记忆树节点模型

系统必须支持节点的创建、修改、删除、移动、读取，并支持：

- 父子层级关系。
- 节点精度等级。
- 节点重要性、稳定度、遗忘速度、主动前馈、访问评分。
- 来源信息与来源类型。
- 最新版本与历史版本。

### FR-002 关联边模型

系统必须支持节点之间的有向关联边，并记录：

- 关系类型。
- 权重。
- 建立原因。
- 建立者与时间。

### FR-003 检索与上下文组装

系统必须支持混合检索，并允许调用方指定：

- 读深度。
- 读广度。
- 关联节点数量。
- 叶子节点数量。
- 精度级别。
- 预算约束。

系统返回结果必须同时包含节点内容、子节点名、关联节点名、来源信息。

### FR-004 导入与建树

系统必须支持从外部文本资料导入，并完成：

- 切分。
- 初始摘要。
- 候选父节点建议。
- 候选关联建议。
- 临时节点写入。
- 后续整理任务触发。

建树算法的运行顺序与系统边界见 [Agent 运行时协议 v0.2](specs/agent-runtime-protocol-v0.2.md)。

### FR-005 Agent 启动与恢复

系统必须支持：

- 初始化加载三个根分支。
- 恢复任务与留言。
- 在上下文接近上限时安全收尾并重启。
- 重启后重新挂载必要上下文，继续执行。

启动流程与根节点挂载见 [Agent 运行时协议 v0.2](specs/agent-runtime-protocol-v0.2.md)。

### FR-006 预算控制

系统必须支持：

- 任务预算。
- Token 预算。
- 子任务预算继承。
- 超预算强制总结与退出。

### FR-007 异步写入

系统必须允许 Agent 在正常输出过程中标注待写入记忆，并由后台统一异步落库。写入失败必须能够回报并重试。

### FR-008 Sub-Agent 与 PR 机制

系统必须支持：

- 主 Agent 创建 Sub-Agent。
- Sub-Agent 在独立分支记忆区工作。
- 以 PR 方式提交修改。
- 审核、评论、合并、驳回。

### FR-009 模块平台

系统必须提供模块化底座，支持：

- 模块 manifest。
- 模块注册表。
- 依赖声明与兼容检查。
- 启停控制。
- 模块级配置。
- 模块级审计。
- 模块贡献点。
- 错误隔离与健康检查。

### FR-010 Web 控制台

Web 控制台第一版必须支持：

- 登录与项目选择。
- 任务面板。
- 记忆树浏览与节点详情。
- 关联图谱。
- 时间线与 PR 审核。
- 评测结果展示。

### FR-011 可观测性与评测

系统必须提供：

- 请求级日志与调用链追踪。
- LLM 调用成本统计。
- 基准任务评测。
- 版本回归对照。
- 失败案例归档。

### FR-012 安全与审计

系统必须对以下操作留痕：

- 节点变更。
- 权限变更。
- 模块启停。
- PR 审核。
- 自动整理。
- 数据导入。

### FR-013 困难任务上下文整理

系统必须支持在复杂任务中，由主 Agent 或辅助 Agent 依据下一步目标对上下文进行修剪与压缩，要求：

- 保留下一步任务的强相关信息。
- 压缩弱相关但可重构信息。
- 写入修剪原因与结果审计。

### FR-014 任务暂停与无感恢复（第二版）

第二版系统必须支持任务暂停功能，要求：

- 暂停在安全停止点生效，而不是粗暴中断当前输出。
- 暂停时写入任务快照、待恢复信息与审计记录。
- 下次启动优先从暂停快照恢复，并尽量无感继续。

### FR-015 泛型工具分发与能力注册

系统必须提供统一的工具分发入口，要求：

- 模块工具以正式描述符注册，而不是私有散装接口。
- Agent 调用工具时统一经过鉴权、调度、审计和错误归一化。
- 工具调用必须形成正式调用记录。

### FR-016 模型能力分析与自动任务分配

系统必须支持按任务阶段和预算自动选模，要求：

- 选模结果形成正式路由决策记录。
- 路由至少考虑质量、成本、延迟、上下文需求。
- Sub-Agent 启动时允许使用与主 Agent 不同的模型。

## 9. 模块化需求

### MR-001 分层边界

系统必须采用 Kernel + Module + Adapter 分层。

- Kernel 负责稳定领域能力和统一治理。
- Module 承载领域增强能力。
- Adapter 负责外部依赖接入。

### MR-002 模块清单

每个模块必须提供 yggdrasil.module.yaml，并至少声明：

- id
- version
- dependencies
- capabilities
- config schema
- event subscriptions
- migrations
- frontend contributions

### MR-003 模块加载与隔离

系统必须支持安装级插拔、配置级启停、部署级隔离。第一版不要求运行时热更新。

### MR-004 模块贡献点

系统至少要开放以下 hook：

- API 扩展
- Worker 扩展
- Agent 工具扩展
- 前端 panel / route / widget 扩展
- 事件订阅扩展

### MR-005 模块契约测试

每个模块必须通过契约测试，证明：

- manifest 合法。
- 依赖满足。
- 配置可解析。
- 对外贡献点可加载。
- 生命周期事件可处理。

## 10. 非功能需求

### 10.1 可靠性

- 长任务必须可恢复。
- 异步写入和事件投递必须具备重试与幂等保障。
- 关键状态变更不得只存在于内存中。

### 10.2 可维护性

- 内核 API 与模块接口必须稳定。
- 领域能力新增优先通过模块扩展，而不是修改核心流程。
- 关键架构决策必须形成 ADR。

### 10.3 可观测性

- 每个任务、每个 AgentRun、每次检索、每次写入都必须可追踪。
- 每次模型调用都必须有成本、时延、结果状态记录。

### 10.4 可追溯性

- 外部信息必须标明来源。
- 复杂推理结果必须保留简要原因链。
- 所有重要变更都必须可回放与对比。

### 10.5 性能

- 首版目标不是极限性能，而是稳定性与正确性。
- 在单项目规模下，常见检索响应应保持在交互式可接受范围内。
- 后续性能优化必须在评测结果上证明收益。

## 11. 数据与接口原则

- 记忆树是主数据，不让临时会话日志替代长期记忆。
- 同步读写走稳定 API。
- 异步流程通过事件总线驱动。
- 模块新增字段时必须声明迁移策略。
- 所有外部集成必须通过 Adapter 层接入。
- 第一版所有关键领域对象都必须携带 projectId，并为后续的 spaceId、branchId 预留扩展位。
- 第一版必须预留 TaskSnapshot 与 paused task state，避免第二版任务暂停时大改状态机。

## 12. 验收指标

- 任务完成率。
- 恢复成功率。
- 召回覆盖率。
- 记忆命中后的人工可用率。
- 平均 Token 成本。
- 平均响应时延。
- 自动整理接受率。
- 模块加载成功率。

## 13. 里程碑

- M0：规格冻结
  - 输出 PRD v0.1、ADR 清单、模块协议初稿。
- M1：文本记忆内核闭环
  - 节点模型、关联模型、版本模型、基础检索跑通。
- M2：任务恢复闭环
  - 启动、写入、预算、重启恢复跑通。
- M3：协作闭环
  - Sub-Agent 分支与 PR 最小可用版本上线。
- M4：工程闭环
  - Web 控制台、评测、可观测性、审计到位。

## 14. 风险

- 风险 1：模块化设计过重，拖慢第一版交付。
  - 应对：只做必要的模块协议和模块宿主，不做过度抽象。
- 风险 2：检索策略复杂，早期效果不稳定。
  - 应对：建立基线、保留规则过滤、用评测驱动迭代。
- 风险 3：Sub-Agent 和 PR 流使链路过长。
  - 应对：先做最小可用流程，不追求复杂审批模型。
- 风险 4：未来高级模块回写内核，破坏边界。
  - 应对：通过 ADR、契约测试和目录结构硬约束边界。

## 15. 未决问题

- 已确定：模块宿主和核心 API 默认拆成独立进程，但第一版可以同机部署。
- 已确定：模块配置采用数据库为主、文件覆盖为辅的模式。
- 已确定：第一版单项目运行，但任务与记忆都应支持项目级 package 导入/导出，并为第二版多项目并行预留 projectId。
- 已确定：第一版不支持第三方前端路由注入。
- 已确定：“我是谁”允许长期改写，但 canonical identity 只能由内核态改写。
- 已确定：建树算法的大规模重排与删减不要求人工审批。
- 已确定：上下文修剪在任何风险级别都不要求人工确认。
- 已确定：共享空间需要同时支持只读挂载、写时复制、双向同步。

## 16. 术语表

- 记忆树：以层级节点与关联边组织的长期记忆结构。
- 根分支：我是谁、我在哪、我要干什么。
- 节点版本：节点在不同时间点的历史快照。
- 模块：可独立启停、声明能力与依赖的功能单元。
- Adapter：对外部模型、媒体、身份、存储等依赖的接入层。
- PR：Sub-Agent 或模块变更提交给主分支的审核单元。
