# RFC 流程

[English Version](README.en.md)

本目录用于记录世界树计划中的重大设计决策。

RFC 不是普通 issue 的替代品，而是对架构、协议、公共接口、兼容性和安全边界等高影响变更进行公开设计、评审和留痕的正式机制。

## 什么时候必须写 RFC

以下情况默认必须写 RFC：

- 修改 Kernel / Module / Adapter 的职责边界
- 修改 Core API、模块清单、Hook、事件或公开协议
- 修改关键数据规格、迁移策略或兼容性承诺
- 引入新的关键基础设施依赖或部署模型
- 调整权限、安全边界、发布模型或许可证策略

## 什么时候不需要 RFC

以下情况通常不需要 RFC：

- 局部缺陷修复
- 不改变公共行为的重构
- 文档补充、错字修正、测试补强
- 明确局部且兼容的性能优化

如果 PR 讨论过程中发现改动实际上触及架构或公共契约，应中止直接实现并补 RFC。

## 文件命名

- 新 RFC 使用 `NNNN-short-title.md` 命名。
- `NNNN` 使用递增编号。
- 从 `0001` 开始编号；`0000-template.md` 仅作模板，不计入正式 RFC。

## 状态

每个 RFC 需要在文档头部声明当前状态：

- `Draft`：草案，尚在讨论
- `Review`：已进入正式评审
- `Accepted`：被接受，可以按文档实现
- `Rejected`：不采纳，但保留历史记录
- `Implemented`：核心实现已落地
- `Superseded`：已被新的 RFC 替代

## 推荐流程

1. 复制 `0000-template.md`，创建新的 RFC 文档。
2. 在 Draft PR 中提交 RFC，描述问题、方案、风险和迁移路径。
3. 维护者与社区围绕 RFC 本身讨论，而不是先写实现。
4. 维护者确认接受后，把状态改为 `Accepted`。
5. 实现 PR 必须链接对应 RFC；如果实现偏离 RFC，需要先更新 RFC。
6. 落地完成后，将 RFC 状态更新为 `Implemented`。

## 最低内容要求

每个 RFC 至少应回答以下问题：

- 现在的问题是什么，为什么值得做
- 明确的范围与非目标是什么
- 方案如何工作，改动哪些公共面
- 兼容性和迁移成本是什么
- 风险、替代方案和回滚方式是什么
- 如何验证方案成立

## 审批规则

- 当前阶段由维护者决定是否接受 RFC。
- 维护者可以要求先补测试计划、迁移计划或风险缓解说明，再继续评审。
- 没有被接受的 RFC，不应直接进入正式实现。
