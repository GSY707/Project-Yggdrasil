# 世界树计划 · 真实用户验证任务包

> 配套计划：`docs/research/real-user-validation-plan-2026-04-30.md`
> 配套评分表：`evaluation/fixtures/real-user-validation/scorecard-template-2026-04-30.csv`

---

## 1. 使用方式

本任务包用于真实用户测试、内部试跑和竞品 A/B 对比。

执行时应遵守下面规则：

1. 每个任务只给出任务卡中的原始描述，不额外补充暗示性提示。
2. 世界树 Agent 与对照组必须使用同一份材料、同一时间盒和同一权限边界。
3. 除非任务卡特别要求，中途不主动帮忙纠偏；只记录用户或评审的人工接管。
4. 每个任务完成后，立即填写评分表，避免事后回忆偏差。

---

## 2. 测试材料准备

建议提前准备 3 类材料包，并固定版本号或提交哈希。

| 材料包 | 用途 | 建议内容 |
|--------|------|----------|
| Pack A | `coding-greenfield` | 一个空白仓库模板，含 Python / Node 基础配置、README、空测试目录 |
| Pack B | `coding-inherit` | 冻结到指定提交的 Project Yggdrasil 仓库 |
| Pack C | `deep-research` | 8 到 12 份研究材料、2 份冲突材料、1 份后续更新材料 |

---

## 3. 通用执行规则

### 3.1 时间盒

| 任务类型 | 建议时间盒 |
|---------|-----------|
| 快任务 | 30 到 40 分钟 |
| 跨会话长任务 | 2 次会话，每次 25 到 40 分钟 |
| 异常恢复任务 | 30 到 45 分钟 |

### 3.2 统一记录项

每个任务至少记录：

- 首次有效输出时间
- 总完成时间
- 人工接管次数
- 人工编辑时长
- 是否通过验收
- 是否愿意继续使用

### 3.3 竞品公平性要求

- 使用同一工作区和同一材料包
- 尽量保持相同模型家族或同档位模型
- 权限保持一致：是否允许联网、是否允许终端、是否允许文件修改
- 使用同一验收标准，不根据系统类型调整及格线

## 4. 任务卡

## 4.1 coding-greenfield

### YGG-CG-01 · 从零搭一个可运行的小工具

- 应用：`coding-greenfield`
- 类型：快任务
- 时间盒：35 分钟
- 材料：Pack A
- 目标：验证首次上手、任务拆解、代码落地和自检能力。

**原始任务描述**

```text
你现在在一个空白仓库里，请从零实现一个命令行工具 `note-index`：

1. 输入一个 Markdown 文件目录。
2. 递归扫描 `.md` 文件。
3. 输出一个 `index.json`，字段至少包含 `path`、`title`、`headings`、`word_count`。
4. 补 3 个自动化测试。
5. 更新 README，告诉用户如何运行。

要求：
- 保持实现简单可维护。
- 先给出最小可交付方案，再补测试和说明。
- 完成后自行验证。
- 如果实现 `word_count`，中文文本不得直接用 `split()` 口径；应显式固定 CJK 统计规则，并在测试和 README 中说明。
```

**验收标准**

- 产出可运行 CLI
- 至少 3 个测试通过
- README 可指导新用户运行
- 目录结构清晰，无明显冗余文件

**重点观察**

- 首次有效输出时间
- 是否会先给最小方案，再逐步收尾
- 是否出现不必要的过度设计

### YGG-CG-02 · 跨会话继续扩展同一工具

- 应用：`coding-greenfield`
- 类型：跨会话长任务
- 时间盒：2 个会话，每次 30 分钟
- 材料：沿用 YGG-CG-01 的仓库
- 目标：验证跨会话连续性、历史决策继承和返工成本。

**第 1 次会话原始任务描述**

```text
在已有 `note-index` 工具基础上继续演进：

1. 增加 `--format markdown|json` 输出选项。
2. 增加一个简单配置文件 `note-index.yaml`。
3. 用最少修改保持向后兼容。

请先说明你准备沿用哪些现有结构，再开始修改。
```

**第 2 次会话原始任务描述**

```text
继续上一次未完成的工作。

要求：
1. 不要推翻之前已经合理的结构。
2. 明确指出上一次的已完成项、未完成项和本次计划。
3. 完成后更新 README 的配置说明。
```

**验收标准**

- 第二次会话能准确承接第一次结果
- 不重复创建同义文件或重做已完成部分
- 新增配置和格式选项可以运行
- README 与实现一致

**重点观察**

- 第二次会话是否需要大量人工提醒上下文
- 是否保留前次架构决策
- 是否明显减少重复劳动

### YGG-CG-03 · 中途中断后 safe-stop / resume

- 应用：`coding-greenfield`
- 类型：异常恢复任务
- 时间盒：40 分钟
- 材料：沿用 YGG-CG-02 的仓库
- 目标：验证 safe-stop、resume 和最终交付一致性。

**原始任务描述**

```text
请继续为 `note-index` 添加一个 `--exclude` 参数，支持排除某些目录或文件模式。

要求：
1. 修改 CLI 参数解析。
2. 补测试覆盖排除逻辑。
3. 更新 README。
4. 在任务进行到一半时会被要求 safe-stop，之后需要 resume 并继续完成。
```

**验收标准**

- 恢复后能直接续做，而不是重来
- 不出现重复文件、重复提交或状态错乱
- 最终测试与 README 一致

**重点观察**

- safe-stop 前后计划是否连续
- 恢复后是否能知道自己做到了哪里
- 是否因为中断导致质量明显下降

## 4.2 coding-inherit

### YGG-CI-01 · 在现有仓库中补一条真实可交付改动

- 应用：`coding-inherit`
- 类型：快任务
- 时间盒：35 分钟
- 材料：Pack B（Project Yggdrasil 固定提交）
- 目标：验证对真实仓库的理解、局部修改和文档一致性。

**原始任务描述**

```text
请在当前 Project Yggdrasil 仓库中补齐 M9 acceptance 的统一执行入口：

1. 在根 `package.json` 中新增一个与现有 eval 命名风格一致的脚本入口。
2. 在 README 中补充对应运行命令。
3. 更新 docs/DIRECTORY_REFERENCE.md，确保目录说明与实际入口一致。
4. 做最小必要验证，不要改动无关部分。
```

**验收标准**

- 改动范围聚焦
- 文档和入口保持一致
- 验证动作合理且可复现
- 不破坏现有脚本命名风格

**重点观察**

- 是否能快速找到正确修改点
- 是否会误改无关文件
- 是否能主动保持 README 与目录索引一致

### YGG-CI-02 · 在现有仓库中定位一次首响偏慢问题

- 应用：`coding-inherit`
- 类型：跨会话长任务
- 时间盒：2 个会话，每次 30 分钟
- 材料：Pack B
- 目标：验证仓库理解、性能定位、证据链和最小修复策略。

**第 1 次会话原始任务描述**

```text
当前用户反馈：任务从启动到第一次有用输出偏慢。

请在这个仓库中：
1. 找到最可能的热路径。
2. 说明你准备如何验证这个怀疑。
3. 优先提出一个最小、可回滚、可验证的改动方案。

如果证据不足，不要盲改，先把证据链说清楚。
```

**第 2 次会话原始任务描述**

```text
继续上一次的首响性能问题处理。

要求：
1. 说明你上次确认了什么、还缺什么。
2. 完成最小改动或给出被证据支持的不改理由。
3. 用最窄验证手段证明结论。
```

**验收标准**

- 能给出可信的热路径证据
- 改动或结论聚焦，不空泛
- 第二次会话不需要从头重查
- 结果可复核

**重点观察**

- 是否能维持性能分析上下文
- 是否会在证据不足时胡乱修改
- 是否能用小验证快速证伪/证实

### YGG-CI-03 · 依赖降级条件下完成一次任务

- 应用：`coding-inherit`
- 类型：异常恢复任务
- 时间盒：40 分钟
- 材料：Pack B + E3 环境（Redis 不可达）
- 目标：验证真实误配场景中的可恢复性和可诊断性。

**原始任务描述**

```text
当前环境中 Redis 不可达，但用户仍希望完成一轮最小任务执行。

请：
1. 判断系统会如何降级。
2. 用最小风险方式完成一次任务执行或验证链路。
3. 明确告诉用户：当前退化了什么、保留了什么、下一步怎么恢复正式状态。
```

**验收标准**

- 能识别并解释 fallback 行为
- 任务或验证链路仍然可完成
- 给出的恢复建议具体且可执行
- 不制造新的误导性配置

**重点观察**

- 是否能把错误翻译成用户可理解的结论
- 是否能避免“依赖一坏就卡死”
- 是否能清晰区分临时降级与正式修复

### YGG-CI-04 · 复杂文件拆分固定回归

- 应用：`coding-inherit`
- 类型：快任务 / 回归任务
- 时间盒：30 分钟
- 材料：Pack B
- 目标：验证复杂文件拆分不再依赖临场发挥，而是能通过固定回归入口持续检查。

**原始任务描述**

```text
请确认当前 Project Yggdrasil 仓库里的复杂文件拆分已经进入固定回归集：

1. 找到 G2 复杂文件拆分回归入口。
2. 说明它覆盖哪些真实拆分样本。
3. 运行最小必要验证。
4. 如果发现旧 monolith 文件、文档漂移或路由层绕过 Service，请做最小修复。

要求：
- 不要重新大规模拆文件。
- 只处理与 G2 复杂文件拆分回归直接相关的文件。
- 交付时明确列出验证命令和结果。
```

**验收标准**

- 存在可重复运行的 G2 回归命令
- 至少覆盖一个真实复杂文件拆分样本
- 验证能检查旧 monolith 不复活、拆分子文件规模、文档同步或架构边界
- 验证命令可在本地无 live provider 的情况下运行

**重点观察**

- 是否能把一次性技术债处理转为固定回归
- 是否避免无关重构
- 是否能清楚区分本地回归已闭合项和仍需 live 复跑的外部证据项

## 4.3 deep-research

### YGG-DR-01 · 基于资料包给出一份可引用结论

- 应用：`deep-research`
- 类型：快任务
- 时间盒：35 分钟
- 材料：Pack C
- 目标：验证资料消化、引用准确性和结论结构化能力。

**原始任务描述**

```text
请基于给定研究资料，输出一份不超过 1 页的结论摘要：

1. 先给出最终建议。
2. 再列出支持建议的 3 到 5 条关键证据。
3. 所有关键结论必须能回指到具体资料。
4. 单独指出目前还不确定的部分。
```

**验收标准**

- 关键结论都有出处
- 没有把冲突材料硬拼成单一结论
- 结构清晰，适合决策阅读

**重点观察**

- 是否能区分事实、推断和不确定项
- 是否能快速形成可用摘要
- 是否有明显幻觉引用

### YGG-DR-02 · 第二次会话接着做研究更新

- 应用：`deep-research`
- 类型：跨会话长任务
- 时间盒：2 个会话，每次 25 到 35 分钟
- 材料：Pack C + 后续更新材料
- 目标：验证研究场景下的长期记忆和结论迭代能力。

**第 1 次会话原始任务描述**

```text
先基于当前资料建立一份研究结论草稿，并列出你认为仍需补充验证的 3 个问题。
```

**第 2 次会话原始任务描述**

```text
这里有一批新增资料，请继续前一轮研究。

要求：
1. 说明哪些结论被新资料强化，哪些被推翻。
2. 保留有效旧结论，不要整份重写。
3. 输出一版更新后的结论摘要，并标注变化点。
```

**验收标准**

- 能清楚区分“延续”和“修正”
- 不丢失前一轮关键证据
- 更新后的结论有变化说明

**重点观察**

- 是否具备连续研究能力
- 是否会因为新资料而忘掉旧证据
- 是否能低成本完成增量更新

### YGG-DR-03 · 研究途中中断后处理冲突证据

- 应用：`deep-research`
- 类型：异常恢复任务
- 时间盒：40 分钟
- 材料：Pack C + 冲突材料
- 目标：验证研究任务在中断与冲突材料出现时的稳定性。

**原始任务描述**

```text
请先形成一版阶段性判断。任务中途会被 safe-stop。

resume 后你会收到一份与当前判断冲突的材料，请：
1. 更新结论。
2. 单独列出被冲突证据影响的结论。
3. 用“已确认 / 高概率 / 待确认”三档表达最终判断。
```

**验收标准**

- 恢复后保留原有证据上下文
- 能正确处理冲突材料，而不是忽略或强行统一
- 最终输出区分不同置信度

**重点观察**

- 恢复后是否还能定位原判断依据
- 是否能在冲突出现后稳住结论结构
- 是否把不确定性表达清楚

## 5. 执行顺序建议

建议按下面顺序执行，避免一上来就进入最复杂任务：

1. 先跑 3 个快任务，测上手摩擦和首响。
2. 再跑 3 个跨会话长任务，测连续性。
3. 最后跑 3 个异常恢复任务，测鲁棒性。

如果在前 3 个任务里已经出现阻塞级误配，应先修复，再进入长任务和恢复任务。
